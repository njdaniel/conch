An ordinary Windows user installs one app, saves their servers, chats, joins voice when they choose, holds a key or Mouse 4 while a game has focus and is heard exactly while it is held, and shares a screen on configurations that were tried. Everything that makes that true today on Linux (the gate, the mixer, the control protocol, the supervision rules) is kept; what changes is the audio device layer, the key source, and how two processes are tied together on an operating system without `/proc/self/fd/3`, process groups or `SIGTERM`.

## 1. Target and toolchain pins

**Decision proposed.** The first Windows client supports **Windows 11 x64, version 25H2 (OS build 26200)** on every edition, and **24H2 (OS build 26100) only on the editions Microsoft still services** (Enterprise and Education to 2027-10-12; LTSC 2024 to 2029-10-09). Microsoft's release table on 2026-10-26 lists 25H2 serviced to 2027-10-12 for Home/Pro and 2028-10-10 for Enterprise/Education; 24H2 Home/Pro is already "End of updates"; 23H2 Home/Pro has ended and its Enterprise/Education servicing ends 2026-11-10 ([Windows 11 release information](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information), checked 2026-10-28). So a Home or Pro machine is supported on 25H2 and nothing older. 23H2 is out entirely. The same table lists two newer released versions: **26H1** (OS build 28000, generally available 2026-02-10, Home/Pro serviced to 2028-03-14) and **26H2** (OS build 26300, generally available 2026-09-29, Home/Pro serviced to 2028-10-10). Neither is excluded and neither is promised: they are **pending validation**, because no experiment has run on them and 26H1's build number (28000) is a different branch from 26100/26200/26300, so nothing measured on 25H2 transfers to it by argument. The classification is therefore: 25H2 **supported** (the primary target; E1 to E12 run on it first); 26H2 **pending validation** (same servicing lineage as 25H2, memory; E1 to E12 rerun on it second); 26H1 **pending validation** (different branch; run when a machine is available, lower priority); 24H2 **supported only on still-serviced editions**; 23H2 and Windows 10 **excluded** (out of servicing or ending within weeks). Since 25H2 is the same servicing branch as 24H2 with features enabled on top (memory), the build-26100 and build-26200 rows of the matrix are expected to behave alike. Windows 10, ARM64 (`aarch64-pc-windows-msvc` is Tier 1 in Rust, but LiveKit ships a `win-arm64` libwebrtc that nobody here has built against) and WSL-hosted audio are outside this target, as #756 says.

## 2. The audio backend

**Decision proposed.** The microphone and speakers on Windows are WASAPI, through the [`wasapi`](https://docs.rs/wasapi/latest/wasapi/) crate (0.26.0, MIT, published 2026-10-11), as a second implementation of the two traits of `conch-voice-audio` (`MicSource`, `SpeakerSink`, `Pacing::Ring`) beside the PipeWire one in `voice/conch-voice/src/audio.rs`. `dmn-audio` becomes a `[target.'cfg(target_os = "linux")'.dependencies]` entry and `wasapi` a `cfg(target_os = "windows")` one; the gate, the mixer, the jitter buffers, the session loop and the control protocol are untouched. **`forbid(unsafe_code)` stays on every crate.** The rule in CLAUDE.md is that native code is reached only through dependencies; `wasapi` is to Windows what `dmn-audio` is to Linux, and nothing is moved anywhere to dodge the rule.

### 2.1 Candidates

| Crate | Version, licence, last publish | Covers what we need | Does not | Note |
| --- | --- | --- | --- | --- |
| [`wasapi`](https://docs.rs/wasapi/latest/wasapi/) | 0.26.0, MIT, 2026-10-11 | WASAPI only; shared and exclusive mode; event-driven buffers; device enumeration and defaults; **device-change notifications** (added, removed, default changed); render-device loopback; a `record_application` example; "the presented API is all safe Rust" | the crate's docs do not spell out process-tree loopback (`ActivateAudioInterfaceAsync` with include/exclude); **pending** E5 | one maintainer (HEnquist). Builds on the `windows` and `windows-core` crates (MIT OR Apache-2.0, memory) |
| [`cpal`](https://docs.rs/cpal/latest/cpal/) | 0.18.2, Apache-2.0, 2026-08-16 ([crates.io](https://crates.io/api/v1/crates/cpal)) | cross-platform (WASAPI, CoreAudio, ALSA, PipeWire, ASIO); enumeration, defaults, input and output streams with error callbacks; data callback on a dedicated audio thread | **no device-change or default-device-change notification; no loopback mentioned** | would also serve macOS (#755). Its abstraction would have to be bent around the two missing features |
| [`windows`](https://crates.io/crates/windows) directly | Microsoft's bindings | everything | its API is `unsafe` throughout | cannot be used under `forbid(unsafe_code)` |

**Why `wasapi`.** The helper's device rules are strict: a named device that goes away is `capture: unavailable` and is never replaced; following `default` means following the default as it changes; a switch during a transmission shuts the gate ([tui-voice.md §20.5](tui-voice.md)). Those rules need to be told when a device is removed or the default changes, which is `IMMNotificationClient` ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient)), and `wasapi` exposes it while `cpal` does not. It is also Windows-only, so it adds nothing to the Linux build and no cross-platform layer that both backends would have to fit. `cpal` stays the alternative if E3 finds `wasapi`'s buffer model or notifications wanting; choosing it would be a reasoned revision, not a fallback made in silence.

### 2.2 Shape of the Windows audio path

```text
WASAPI capture (event-driven, shared) ─► capture ring ─► transmit gate ─► LiveKit track
remote tracks ─► jitter buffers ─► mixer ─► playback ring ─► WASAPI render (event-driven, shared)
```

- **Threads.** `wasapi`'s event-driven mode wakes a thread of ours on the engine's event each period; that thread moves samples between the WASAPI buffer and the lock-free rings and does nothing else, as `dmn-audio`'s callbacks do. The transmit and mix tasks look at the rings every `RING_LOOK` as they do today; nothing in the pacing changes (`Pacing::Ring`: the sound card's clock sets the pace).
- **Format.** Everything inside is 48 kHz mono f32 in 10 ms frames. Shared-mode WASAPI gives the engine's mix format; the plan is to ask the engine to convert (`AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM` with `SRC_DEFAULT_QUALITY`; from memory, Windows 8.1 and later) so that no resampler crate is needed. If `wasapi` does not expose those flags, or the engine refuses mono, the helper downmixes and resamples itself; a resampler would be one more crate and is **pending** E3.
- **Period.** 10 ms is requested; `IAudioClient3` lets a client ask for a specific periodicity in shared mode ([About WASAPI](https://learn.microsoft.com/en-us/windows/win32/coreaudio/wasapi)). The engine may give its default. The ring targets (`TARGET_FILL`, `CAPTURE_RING_MS`) are tuned per backend, not shared constants.
- **Device identity.** A device is named by its **endpoint ID string**, which Microsoft says "uniquely identifies the device with respect to all of the other audio endpoint devices in the system" and must be treated as opaque: "the string format is undefined and might change from one implementation of the MMDevice API system module to the next" ([IMMNotificationClient](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient)). The form seen in practice is `{0.0.0.00000000}.{guid}` (memory), ASCII and under sixty bytes, but **nothing guarantees ASCII, a length, or the absence of `\`**, so compatibility with the `set_devices` name rule (1 to 255 bytes, one line, no control character, no `"` or `\`, so that it can be written into `voice.toml` between quotes; [tui-voice.md §20.3](tui-voice.md)) is **checked per device, never assumed**. The Windows lister applies the rule the Linux lister already applies to PipeWire names (`fit_for_the_config` in `voice/conch-voice/src/devices.rs`): an endpoint whose ID fails it is **counted in `unshown_microphones`/`unshown_speakers` and cannot be chosen**, and a `set_devices` naming such an ID is `invalid` as any bad name is. No mapping from IDs to names (hashing, escaping) is proposed: it would be a new rule for a wire field and would need the owner's sign-off, and until E4 records real IDs there is no evidence it is needed. So **`set_devices` carries endpoint IDs on Windows and PipeWire node names on Linux, with no change to the wire shape**, under the existing validation; the text of §20.3 that says "a PipeWire `node.name`" becomes "the backend's stable device name" when #776 lands. The friendly name is the description. The IDs' actual form, and their stability across replugs, are E4 observations.
- **Device loss.** A stream error of `AUDCLNT_E_DEVICE_INVALIDATED` ("Frequently, the application can recover from this error", [About WASAPI](https://learn.microsoft.com/en-us/windows/win32/coreaudio/wasapi)) or an `OnDeviceRemoved` for the device in use is the device going away: the gate shuts with no tail, the state shows `capture: unavailable` and `no_microphone`, and nothing is substituted. `OnDefaultDeviceChanged` matters only when the side follows `default`; then the stream moves to the new default, and if a transmission is under way it ends first, as a `set_devices` to a new microphone does (§20.5). Callbacks "must be nonblocking" and must not release the final reference to an MMDevice object (same page): the notification handler posts to the session loop and returns.
- **Microphone privacy.** Windows 11's "Let desktop apps access your microphone" applies to all desktop apps at once ("Desktop apps cannot be individually toggled"), and Microsoft warns that desktop apps "might still be able to access your camera or microphone even when these settings are turned off" ([Windows camera, microphone and privacy](https://support.microsoft.com/en-us/windows/windows-camera-microphone-and-privacy-a83257bc-e990-d54a-d212-b5e41beba857)). What the helper sees when the toggle is off (an error at `Initialize`, or silence) is **pending** E4; whichever it is, the state says `no_microphone` or the start fails `audio_unavailable`, and the client's text names the setting.
- **Echo.** WASAPI has `IAcousticEchoCancellationControl`, which lets a capture client name the render endpoint as the reference ([About WASAPI](https://learn.microsoft.com/en-us/windows/win32/coreaudio/wasapi)). That is a possible answer to #186 on Windows, through the engine rather than the SDK; it is not promised, not measured, and is F10. Until measured, the Windows helper says what the Linux one says: wear headphones.

### 2.7 Configuration files on Windows (missing from the first draft)

The configuration layer is Unix-only today and will not compile for the Windows target as it stands:

- `voice/conch-voice/src/cli.rs` imports `std::os::unix::fs::MetadataExt` unconditionally (line 29) and refuses a `voice.toml` by its mode bits (`meta.mode() & 0o777`, line 625);
- `voice/conch-voice/src/config_cmd.rs` imports the Unix `MetadataExt`, `OpenOptionsExt` and `PermissionsExt` (line 35), writes the replacement file with a mode, opens with a hand-defined `O_NONBLOCK` (lines 52–55, 196) so that a FIFO planted at the path cannot block it, and checks that the file it opened is the one it inspected by `(dev, ino)` (line 202);
- `voice/crates/conch-voice-api/src/login.rs` is already `#[cfg(unix)]` for its mode check and says "elsewhere there is no group/other rule to apply" (lines 182–183).

The Windows port, as a follow-up of its own (F15), covers:

1. **Discovery.** `CONCH_CONFIG_DIR` first, as today. Without it, the Windows default must be the one the Go client uses on Windows so that the TUI and the helper agree (the shared rule is `internal/cli/testdata/config-dir-vectors.json`); Go's `os.UserConfigDir` returns `%AppData%` on Windows (memory), so `%APPDATA%\conch` is the expected answer, **pending** a reading of `cli.ConfigDir` for Windows and an added vector.
2. **Protected access.** Mode bits do not exist; the honest replacement is the one `login.rs` already made: no group/other check on Windows, with the protection coming from `%APPDATA%` being readable by the user, SYSTEM and Administrators only under its default DACL (memory; recorded at E12). An ACL check from safe Rust is not possible without a Win32 binding; if the input dependency of §4.3 brings `windows-sys` into the tree through a reviewed crate, reading the file's DACL can be added there later. The documentation says plainly that on Windows the helper trusts the directory, not the file.
3. **Replacement semantics, and the race.** `std::fs::rename` over an existing file replaces it on Windows (memory: `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`), so the write-temporary-then-rename shape of `config_cmd.rs` is **kept**: writing through an already-open handle was the first draft's idea and is wrong twice over, since it loses the atomic replacement and leaves a partial file if the process is interrupted mid-write. The race `config_cmd.rs` guards against on Linux (a symlink swapped in between `symlink_metadata` and the open, so that the open follows it elsewhere) exists on Windows too, and the first draft's "open once" does not close it: an ordinary `CreateFileW` follows a symbolic link ("if an existing file is opened and it is a symbolic link, the handle returned is a handle to the target", [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), Symbolic Link Behavior), and nothing about the opened handle proves it is the directory entry that was inspected, because the stable identity fields are missing (`std::os::windows::fs::MetadataExt::file_index` and `volume_serial_number` are "nightly-only experimental" under `windows_by_handle`, [MetadataExt](https://doc.rust-lang.org/std/os/windows/fs/trait.MetadataExt.html)). The Windows rule is therefore: **open with `FILE_FLAG_OPEN_REPARSE_POINT`**, through `std::os::windows::fs::OpenOptionsExt::custom_flags` (stable since 1.10, a safe method that "sets extra flags for the `dwFileFlags` argument", [OpenOptionsExt](https://doc.rust-lang.org/std/os/windows/fs/trait.OpenOptionsExt.html)), so that a symbolic link is opened as itself and not followed (same CreateFileW section: with the flag, "the handle returned is a handle to the symbolic link"); then **reject the opened handle if `File::metadata().file_attributes()` carries `FILE_ATTRIBUTE_REPARSE_POINT`** (`file_attributes` is stable, [MetadataExt](https://doc.rust-lang.org/std/os/windows/fs/trait.MetadataExt.html); the constant's value is from the Windows file-attribute constants, memory: 0x400) or is not an ordinary file. That makes the check on the handle itself, which a swap after inspection cannot defeat, and it needs no identity fields. The pre-open `symlink_metadata` check stays as the early, friendly refusal. **Conflict detection** on the write path is kept as on Linux: the temporary is created with `create_new`, and just before the rename the file is read again and compared with the snapshot taken when it was loaded, **its text included**, as `config_cmd.rs` does today (`Snapshot` holds the text with the mode and identity, and `Snapshot::take(&path)? != before` refuses with `ConfigChanged`, lines 140–155). On Windows the snapshot is the text plus size and attributes; metadata alone is not enough, since a same-length edit made through a handle still open need not change the modification time until that handle closes ([File Times](https://learn.microsoft.com/en-us/windows/win32/sysinfo/file-times)). A mismatch is reported as "changed meanwhile". Named pipes cannot be planted in a user directory (they exist only under `\\.\pipe\`), so `O_NONBLOCK` has no Windows counterpart to port.
4. **Tests.** The existing `cfg(unix)` tests stay; `cfg(windows)` tests cover discovery with and without `CONCH_CONFIG_DIR`, a reparse point at the path, **a swap of the path between inspection and opening** (a regular file inspected, replaced by a symbolic link to another file before the open; the open with the flag must return the link, the attribute check must refuse it, and the other file must be untouched: the test is in the shape of the Linux `symlink` cases of `config_cmd.rs`), replacement while another handle is open (Windows sharing violations are a failure mode Linux does not have), an interrupted write leaving the original intact, and a read-only file. They run in the Windows CI job (F1). Creating a file symbolic link on Windows needs a privilege or developer mode (memory); the test uses a junction or `std::os::windows::fs::symlink_file` and skips with a named reason when it cannot create one, never silently.

Until F15 lands, no Windows binary exists; it is on the critical path of #776 and is listed in §12 as work, not as a sign-off.

## 3. The managed transport on Windows

**Decision proposed.** The owner (the Electron main process; later perhaps the Go TUI) starts `conch-voice.exe managed --events-pipe <name>` with **standard input as the command channel, exactly as today**, and **a named pipe the owner created as the events channel** in place of file descriptor 3. The helper opens the pipe by name with `tokio::net::windows::named_pipe::ClientOptions::open` (safe, overlapped; §3.3), writes one **attach** line that binds this connection to the process the owner spawned, then the hello, and the session proceeds in v1 or v2 with no change to any message. Owner loss is **EOF on standard input or EOF on the events pipe, whichever comes first**; the parent-pid watch of Linux is replaced by that second EOF.

**The invariant that makes this safe, stated first:** **authority arrives only on standard input, from the spawning process.** The events pipe carries none: it is helper-to-owner only, and nothing read from it can cause a join, a publish or an unmute. A hijacked or observed events pipe therefore costs confidentiality of state lines (which hold no secret and no free text) and availability (the owner sees no attach and fails the join closed); it cannot open the microphone. Standard input is trusted because the owner holds its write end and the helper the inherited read end from spawn, and nothing connects to it by name afterwards; libuv implements it as a named pipe under `\\?\pipe\uv\` with the same default DACL as any other ([libuv `pipe.c`](https://raw.githubusercontent.com/libuv/libuv/v1.x/src/win/pipe.c), `uv__create_stdio_pipe_pair`), which is why the trust rests on the handles, not on the name.

### 3.1 Why not file descriptor 3

Node's `child_process.spawn` can open a fourth pipe (`stdio: ['pipe', 'pipe', 'pipe', 'pipe']`), and the docs say extra pipes "are not actual Unix pipes and therefore the child process can not use them by their descriptor files" ([Node child_process](https://nodejs.org/api/child_process.html)). On Windows libuv passes the handle to the child, but a Rust process has no safe way to take an inherited handle by number: `FromRawHandle::from_raw_handle` is `unsafe`. Go's `os/exec` says outright "ExtraFiles is not supported on Windows" ([os/exec](https://pkg.go.dev/os/exec#Cmd)). So fd 3 is a Linux fact, and the issue's wording ("dedicated protocol channel separate from native stdout, tightly scoped inherited handles or appropriately protected/authenticated named pipes") is right to offer the alternatives.

### 3.2 Options weighed

| Option | For | Against |
| --- | --- | --- |
| **A. Events on standard output** (two anonymous pipes, nothing else) | No name, no secret, no new shape; Node and Go both do it; Rust `std::io::stdout` is safe | The Linux design moved events off fd 1 because anything linked into the process may write there; libwebrtc is C++ and `webrtc-sys` is not ours. A stray line is a `bad_event` and the owner stops the helper: it fails closed, but a voice session is lost to a log line. Whether libwebrtc writes to stdout on Windows is **pending** E2 |
| **B. Events on an owner-created named pipe, with an attach line** (proposed) | Keeps the Linux invariant that nothing but the protocol writer touches the channel; needs no Win32 call on either side (Node `net.createServer().listen(path)`; tokio's named-pipe client in Rust); owner loss is an EOF the helper can read; the cross-user boundary is the pipe's DACL (§3.5) | A name in the pipe namespace is enumerable by every local user, who may open it read-only under the default DACL (§3.5); same-user code is not kept out by anything (it never is); one new one-line shape binds the connection to the spawn as defence in depth |
| C. An inherited handle number in argv, `from_raw_handle` in the helper | Smallest surface | `unsafe`; refused |
| D. A localhost TCP listener | Trivially portable | Rejected by #775 ("No unauthenticated localhost listener") and by the Linux design: any process on the machine can connect, and a browser can be made to |
| E. The helper creates the pipe and the owner connects | The Rust side would hold the DACL | Creating a named pipe with a security descriptor needs Win32 (`CreateNamedPipeW` with `SECURITY_ATTRIBUTES`), `unsafe` in Rust; and Node cannot verify a server's pid either |

### 3.3 The channels

| Channel | Created by | Owner's end | Helper's end | Carries |
| --- | --- | --- | --- | --- |
| standard input | libuv (`stdio[0] = 'pipe'`): an anonymous named pipe, the child end a synchronous inherited handle ([libuv `pipe.c`](https://raw.githubusercontent.com/libuv/libuv/v1.x/src/win/pipe.c): `uv__create_stdio_pipe_pair`, client end without `FILE_FLAG_OVERLAPPED` unless asked) | writes commands | `std::io::stdin`, read with `read_bounded` as today | commands, owner → helper. EOF is owner loss |
| events pipe | the owner: `net.createServer().listen('\\\\.\\pipe\\conch-voice-' + id)`, `id` 128 bits from `crypto.randomBytes` in hex; no `readableAll`/`writableAll` (both default `false`, [Node net](https://nodejs.org/api/net.html)) | reads lines; writes nothing, ever | `tokio::net::windows::named_pipe::ClientOptions::new().read(true).write(true).open(name)`: a safe function, needing tokio's `net` feature, which "Opens the named pipe identified by `addr`" with `CreateFile` and `OPEN_EXISTING`, documents the bounded `ERROR_PIPE_BUSY` retry (the pipe exists but no instance is waiting; retry after a short sleep), and by default sets `SECURITY_SQOS_PRESENT` with `SECURITY_IDENTIFICATION` so that the server cannot impersonate the helper ([ClientOptions](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.ClientOptions.html)). The result implements `AsyncRead` and `AsyncWrite` ([NamedPipeClient](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.NamedPipeClient.html)), so it is split into independent read and write halves with `tokio::io::split` | events, helper → owner, on the write half. The read half is read **concurrently**: the owner never writes, so the only thing that read returns is EOF or an error, and either is owner loss. **Why not `std::fs::OpenOptions`:** a synchronous handle serialises I/O on one file object, so a read pending for EOF would block every event write until the owner exits; Microsoft's description of overlapped mode is that it is what lets a thread "perform simultaneous read and write operations on the same pipe handle" ([CreateNamedPipeW](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew)), and tokio's client is the overlapped, safe way to get it. The `net` feature of tokio is a feature flag on an allowed crate, already used by this crate's tests; whether it adds anything to `Cargo.lock` is recorded at E1 |
| standard output | libuv pipe | drained and discarded | whatever the process and its libraries print | nothing of the protocol |
| standard error | libuv pipe | bounded, sanitized tail (Diagnostics, as §14 of tui-voice.md) | the logger | diagnostics |

The pipe name is passed in argv. It is not a secret: argv is readable by every process of the same user, and the pipe namespace is listable by anyone, which is exactly why it carries no authority. The owner spawns with `windowsHide: true` ("Hide the subprocess console window that would normally be created on Windows systems", [Node child_process](https://nodejs.org/api/child_process.html)) so that a console does not flash, and without `detached`.

### 3.4 Attach: binding the connection to the spawn (defence in depth, not authentication)

A random 256-bit **nonce** from `crypto.randomBytes` goes to the helper in its **environment** (`CONCH_VOICE_ATTACH`), beside `CONCH_TOKEN` when `credential: env` is used, and nowhere else: not in argv, not in `voice.toml`. The environment of a process is readable by processes of the same user and by administrators, not by other ordinary users; the same reasoning that already puts `CONCH_TOKEN` there ([tui-voice.md §9](tui-voice.md)). The helper's first line on the events pipe is:

```json
{"schema": "conch.voice_control_pipe.v1", "kind": "attached", "nonce": "<base64url, 43 characters>"}
```

and its second line is the v1 hello.

**What the attach line is, and is not.** It lets the owner tell the connection made by the process it spawned apart from a connection made by some other local user who opened the pipe read-only (§3.5): that is a **spawn-to-pipe binding**. It is **not authentication** of either side, and the schema's documentation and the ADR amendment must not call it that:

- it authenticates nothing **to the helper**: same-user code may create a further instance of the owner's pipe name with `CreateNamedPipeW` (the creator owner has full control, and libuv's listener is `PIPE_UNLIMITED_INSTANCES`, so another instance is permitted; [CreateNamedPipeW](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew), [Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)), and the helper's `CreateFile` may land on that instance, delivering the attach line and every event to the hijacker. The helper cannot tell. **Same-user code is out of scope**, on Windows as on Linux: it can read `CONCH_TOKEN` from the environment and the helper's memory directly; the hijack is named here so that nobody later mistakes the nonce for a defence against it;
- it does not need to authenticate anything **to the owner** across users either, because the DACL already denies other users write access (§3.5): a cross-user client can open the pipe read-only and cannot deliver a line. The nonce is defence in depth for that case, and it is what distinguishes the spawned helper from any same-user process that connected without reading the environment.

The owner's rules, all of them requirements for #776:

1. the listener is created with no `readableAll`/`writableAll`; the name and the nonce both come from `crypto.randomBytes`; a `listen` failure on the name (a squat; `FILE_FLAG_FIRST_PIPE_INSTANCE` makes it `ERROR_ACCESS_DENIED`) picks a new random name;
2. each connection has a **first-line deadline** (the remaining part of `VoiceControlHelloTimeoutMS` from the spawn) and the **4096-byte line cap**; the first line must be a well-formed `attached` whose nonce matches under `crypto.timingSafeEqual`; otherwise the connection is closed;
3. the owner **never writes** to any connection, attached or not;
4. the listener is **closed on attach or on the deadline**; after attach, no further connection is accepted;
5. the nonce is **redacted from diagnostics**: the owner's stderr tail and status views never show it, and the attach shape's `sensitive.json` fixture asserts that no field but `nonce` could hold a secret-shaped value and that the nonce itself is not echoed in any later event;
6. the helper writes the attach line once, never reuses a nonce, and forgets it after writing.

**About the principle.** The Linux contract says no secret crosses the channel in either direction, so that a transcript can be logged and shown without a second thought ([tui-voice.md §4](tui-voice.md), [pkg/schema/voice_control.go](../../pkg/schema/voice_control.go)). The nonce is a one-time binding value spent the moment the owner reads it; a transcript that shows it reveals nothing reusable, and rule 5 keeps it out of diagnostics anyway. The property that matters is kept: **no login token, join token or room name is ever on the channel, and nothing on the events pipe carries authority.** The attach line is a new wire shape and must live in `pkg/schema` with golden fixtures and a `sensitive.json` of its own; the Go reader applies the framing rules of §3 of tui-voice.md (one object per line, 4096 bytes, unknown fields ignored). It is Windows-only in use but platform-neutral in shape, so a Linux owner that later wanted a named pipe could use it. **Needs the owner's sign-off** (schema) and a `security-reviewer` pass on this section; F4.

Why not pass the nonce on standard input before `start`: it would change the first-line rule of v1 (the first command is `start`) and put a secret-shaped value in the command transcript; the environment already carries one secret by design and the attach line is read only by the owner.

### 3.5 Who can connect, and what they get

- libuv creates the listener with `PIPE_ACCESS_DUPLEX | FILE_FLAG_OVERLAPPED | WRITE_DAC` (first instance also `FILE_FLAG_FIRST_PIPE_INSTANCE`), `PIPE_TYPE_BYTE | PIPE_READMODE_BYTE | PIPE_WAIT`, `PIPE_UNLIMITED_INSTANCES`, and **`NULL` security attributes**; `PIPE_REJECT_REMOTE_CLIENTS` is **not** set ([libuv `pipe.c`](https://raw.githubusercontent.com/libuv/libuv/v1.x/src/win/pipe.c), `pipe_alloc_accept`; the version shipped in the pinned Electron is to be re-read at #770).
- With `NULL` security, "the ACLs in the default security descriptor for a named pipe grant full control to the LocalSystem account, administrators, and the creator owner. They also grant read access to members of the Everyone group and the anonymous account" ([CreateNamedPipeW](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew)).
- `FILE_FLAG_FIRST_PIPE_INSTANCE` means a squatter who pre-creates the name makes the owner's `listen` fail with `ERROR_ACCESS_DENIED` (same page); the owner then picks a new random name. The owner never connects as a client to a pipe it did not create, so there is no server to impersonate.
- **The DACL is the cross-user boundary.** Another ordinary user, and (because remote clients are not rejected and the anonymous account has read access) possibly a remote one over SMB if the firewall and null-session policy allow it, can open the pipe **read-only**: `GENERIC_READ` is granted to Everyone, `GENERIC_WRITE` is not, and creating a further instance needs `FILE_CREATE_PIPE_INSTANCE`, which only the creator owner, administrators and SYSTEM hold ([Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights): "the DACL must allow the calling thread FILE_CREATE_PIPE_INSTANCE access"). So a cross-user client cannot deliver a line and cannot hijack an instance; it holds one instance open and reads, and reads nothing, because the owner writes nothing. What it learns is that a pipe with Conch's prefix exists. **Same-user code is not kept out** (it may read, write and create instances; §3.4 names the hijack) and is not meant to be: it is already on the trusted side of every boundary this design has.
- **Residuals.** A denial-of-service against the attach (a flood of instances before the helper connects, bounded by the first-line deadline and the line cap; the join fails closed) and the pipe's existence naming the product. Both are in the review document, with the hardening a Win32-capable owner (the Go TUI) could add later: a DACL for the user's logon SID only (which Microsoft names as the way "to prevent remote users or users on a different terminal services session from accessing a named pipe", same page), `PIPE_REJECT_REMOTE_CLIENTS`, and `GetNamedPipeClientProcessId` compared with the spawned pid.
- **To record at E2:** from a second standard user, `GENERIC_WRITE` on the owner's pipe is denied and `GENERIC_READ` succeeds; from the same user, `CreateNamedPipeW` on the owner's name succeeds (the hijack is real); the effective DACL and integrity label of the pinned Electron's pipe as `GetSecurityInfo` reports them.

| Linux (tui-voice.md §8) | Windows | Why |
| --- | --- | --- |

| parent pid changes (`std::os::unix::process::parent_id`, polled every `VoiceControlOwnerPollMS`) | **EOF or error on the events pipe**, read by a thread that only ever sees the end | `parent_id` is Unix-only in `std`; there is no safe way to wait on another process on Windows. The events pipe's server end is in the owner alone and not inheritable (libuv does not mark listeners inheritable), so a stray inherited standard-input handle in some other process cannot keep the helper alive. | `SIGTERM`/`SIGINT` are `leave` with reason `signal` | tokio's `signal::windows` (`ctrl_c`, `ctrl_break`, `ctrl_close`, `ctrl_shutdown`) are `Input::Signal` | with `windowsHide` there is no console, so these arrive only from a logoff or shutdown; the reason stays `signal` |

The bounds are the contract's and are unchanged: gate shut within `VoiceControlGateShutMS` of noticing, capture stopped within `VoiceControlCaptureStopMS`, process gone within `VoiceControlOwnerLossExitMS`; measured in E6.

### 3.7 Credentials to the helper

The Electron shell holds the token (§9.1) and starts the helper with `credential: env` and `CONCH_TOKEN` in the child's environment, as the TUI does when its own token came from the environment. **`credential: stored` is not honoured by the Windows helper in the first version:** the stored-login check in the Rust client is "a regular file, not readable by others" by Unix mode bits, which has no meaning on NTFS; rather than invent an ACL check, the Windows helper reads no `credentials.json` and answers a `stored` start with `failed`, reason `not_signed_in` (literally true: it has no stored login). No new reason, no schema change.

**The child's environment is built from empty, not filtered.** Windows environment variable names are case-insensitive (memory; the Win32 convention), so the Linux rule "remove every name beginning with `CONCH_`" would let `Conch_Token` through a case-sensitive `startsWith('CONCH_')`. The owner therefore starts from an empty environment and adds, by a **case-insensitive allowlist**, only what the helper and its libraries need to run: `SYSTEMROOT`, `PATH`, `TEMP`, `TMP`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `PROGRAMDATA`, `COMSPEC` (the list is confirmed at E1 by running the helper with exactly these); then it sets `CONCH_CONFIG_DIR` when the profile has one, `CONCH_TOKEN`, and `CONCH_VOICE_ATTACH`. Nothing else, so `RUST_LOG` and `RUST_BACKTRACE` are absent by construction. **The helper cannot scrub its own environment:** `std::env::set_var` and `remove_var` are `unsafe fn` ([std::env::set_var](https://doc.rust-lang.org/std/env/fn.set_var.html)), which `forbid(unsafe_code)` excludes; the helper spawns no process today, and if it ever did, the child would get `Command::env_clear()` plus the same allowlist. The Linux supervisor's filter is correct on Linux, where names are case-sensitive; making it an allowlist too is a reasonable harmonisation but not required by this design.

**Platform-neutral.** Every message, every bound, the handshake, the ordering rules, the state machine, the owner-side `Status` and the fixtures. `managed.rs` gains a Windows channel module (open the pipe, write attach, read-for-EOF) and loses nothing.

**Open questions.** E2 (tokio's named-pipe client against libuv's listener: events written for a minute while an EOF read is pending, then owner exit, with both the writes and the EOF arriving; the cross-user and same-user access checks of §3.5; the effective DACL and integrity label; libwebrtc's stdout behaviour), E6 (owner crash with the key held; stdin leak through Electron's other children; job membership; measured exit times). **Follow-up:** F4, F5.

## 4. Global push-to-talk

**Decision proposed.** The helper registers for **Raw Input** from the keyboard and mouse top-level collections with `RIDEV_INPUTSINK | RIDEV_DEVNOTIFY` on a message-only window of its own, and turns the device's own **transitions** into presses and releases: a keyboard `RI_KEY_MAKE` while the bound key is up is a press, `RI_KEY_BREAK` is a release; `RI_MOUSE_BUTTON_4_DOWN`/`_UP` and `RI_MOUSE_BUTTON_5_DOWN`/`_UP` likewise. A `MAKE` while the key is already down (auto-repeat) is nothing. These feed the existing push-to-talk machine in `conch-voice-control` through the same `Input::Key` the evdev watcher uses; nothing downstream knows the operating system.

### 4.1 What the documentation establishes

- "An application can receive data when it is in the foreground and when it is in the background (if registered with `RIDEV_INPUTSINK`)" ([Raw Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input), page dated 2025-07-14). Registration needs a window (`hwndTarget`); a message-only window will do.
- Mouse buttons are reported as transitions: `RI_MOUSE_BUTTON_4_DOWN` 0x0040 "XBUTTON1 changed to down", `RI_MOUSE_BUTTON_4_UP` 0x0080, `RI_MOUSE_BUTTON_5_DOWN` 0x0100, `RI_MOUSE_BUTTON_5_UP` 0x0200 ([RAWMOUSE](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawmouse)). Mouse 4 and 5 are therefore first-class, with their own up events; this is what the issue asks for.
- Keyboard events carry `MakeCode` (the scan code), `Flags` with `RI_KEY_MAKE` 0 ("The key is down") and `RI_KEY_BREAK` 1 ("The key is up"), the `E0`/`E1` prefixes, and `VKey` ([RAWKEYBOARD](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawkeyboard)). Bindings are by scan code with its prefix, not by virtual key, so a layout change does not move the talk key (the Linux client binds by `KEY_*` code for the same reason).
- Microsoft itself steers away from hooks: "In most cases where the application needs to use low level hooks, it should monitor raw input instead" ([LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)).

### 4.2 Options weighed

| Backend | Press and release | Background | Why not |
| --- | --- | --- | --- |
| **Raw Input** (proposed) | yes, from device transitions | yes (`RIDEV_INPUTSINK`) | — |
| `WH_KEYBOARD_LL`/`WH_MOUSE_LL` hooks | yes | yes | "If the hook procedure times out ... on Windows 7 and later, the hook is silently removed without being called. There is no way for the application to know whether the hook is removed"; the cap is 1000 ms ([LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)). A removed hook is a release never seen. Global hooks are "a shared resource" to be "restricted to special-purpose applications" ([SetWindowsHookExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)); hooks are also what anti-cheat software looks for (memory, §5) |
| Electron `globalShortcut` / `RegisterHotKey` | activation only | yes | no release; swallows the key from the game. ADR-007 already says "Keyboard shortcuts alone are insufficient proof" |
| polling `GetAsyncKeyState` | by sampling | yes | misses presses shorter than the poll, costs a wake per poll, and is Win32 FFI anyway |
| a kernel driver, injection into the game | — | — | excluded by #756 ("No driver/injection/anti-cheat bypass") |

### 4.3 The dependency question

Raw Input is Win32: `RegisterRawInputDevices`, a window class, a message loop, `GetRawInputData`. Under `forbid(unsafe_code)` the helper cannot call them. Three routes, in the order to try them:

1. **[`winit`](https://docs.rs/winit/latest/winit/) 0.30.13** (Apache-2.0, published 2026-10-24; [crates.io](https://crates.io/api/v1/crates/winit)). Its Windows backend registers exactly `RIDEV_DEVNOTIFY | RIDEV_INPUTSINK` for `DeviceEvents::Always` ("receive events even if we're not in the foreground"), on both the mouse and keyboard collections, and maps `RI_MOUSE_BUTTON_4_DOWN`/`UP` to a pressed/released state for button index 3 ([`raw_input.rs` at v0.30.13](https://raw.githubusercontent.com/rust-windowing/winit/v0.30.13/src/platform_impl/windows/raw_input.rs)); `DeviceEvent::Key` and `DeviceEvent::Button` are "delivered regardless of input focus" ([DeviceEvent](https://docs.rs/winit/latest/winit/event/enum.DeviceEvent.html)). `EventLoopBuilderExtWindows::with_any_thread` lets the loop run off the main thread, which the helper needs because its main thread is tokio's ([EventLoopBuilderExtWindows](https://docs.rs/winit/0.30.13/winit/platform/windows/trait.EventLoopBuilderExtWindows.html)). **Against:** it is a windowing framework in an audio helper, with a large dependency tree that `cargo deny` must clear; 0.31 is in beta and may change `DeviceEvent`; its `MAKE`/`BREAK` to `ElementState` mapping lives in a file not read here (the raw-input file does not read the break flag), and must be checked in E7 before trust. Try it first, `default-features = false`, `cfg(windows)` only.
2. A smaller maintained crate exposing Raw Input safely. None was evaluated here (crates such as `multiinput` exist but were **not checked** for maintenance or licence); E7 includes a short survey before settling on `winit`.
3. **A reviewed policy change:** one crate, `conch-voice-input-windows`, allowed `unsafe` only in a leaf module that binds `windows-sys` for the dozen calls needed, reviewed line by line, with `forbid(unsafe_code)` kept everywhere else. This needs an amendment to ADR-006 and CLAUDE.md rule 6 and is the fallback, not the plan; #775 says "Do not move code to another package/repository merely to evade that rule", and this route does not: it names the exception and asks for it.

Each route is a new dependency or a policy change and **needs Nick's sign-off**; F6.

**Audit of the chosen dependency, at its pinned version, before it is allowed (requirements for F6 and #777):** the registration flags are exactly `RIDEV_INPUTSINK | RIDEV_DEVNOTIFY` on the keyboard and mouse collections, never `RIDEV_NOLEGACY` (which would take ordinary input away from the helper's own window and, misconfigured, from others) and never `RIDEV_CAPTUREMOUSE`; `SetWindowsHookEx` does not appear anywhere in the vendored source that is compiled for the helper; the dependency's logging and tracing features are off (`default-features = false`, and `cargo tree -e features` checked), so no key or scan code can reach a log through it; and the existing "no scan code in any output" test of the key path is rerun on Windows against the helper's stderr and events. For `winit` 0.30.13 the flag part is already read in source ([`raw_input.rs`](https://raw.githubusercontent.com/rust-windowing/winit/v0.30.13/src/platform_impl/windows/raw_input.rs)); the rest is E7.

### 4.4 Fail-closed rules on Windows

Every rule of [conch-voice.md §3 and §4](conch-voice.md) applies. The Windows specifics:

- **Repeats never hold or reopen the gate, and an unknown initial state is not a press.** The machine ignores a `MAKE` for a key it already holds; only `BREAK` releases. That alone is not enough on Windows: Raw Input has no way to ask whether a key is currently down from safe code, so a binding whose key is **already held when the helper registers** would see its first `MAKE` as an auto-repeat and, with no record of the key being down, would count it as a fresh press, opening the gate on a key nobody just pressed. So **a binding starts in an unknown state and is armed only by an observed `BREAK`**: until that first release, `MAKE`s for it are ignored. The same arming applies after `max_transmit_secs` shuts the gate on a held key: the repeats that keep arriving are `MAKE`s for a key the machine still holds and change nothing, and a `BREAK` then a `MAKE` are needed to transmit again, as on Linux. Cost: a key held across the helper's start transmits nothing until released once; that is the fail-closed side. E7 tests both: start the helper with the talk key held (nothing transmits; release; press; transmits), and hold past `max_transmit_secs` (one transmission ends at the bound; repeats do not reopen; release and press reopen).
- **A stalled input thread shuts the gate.** If the thread that pumps Raw Input messages stops delivering for longer than one `VoiceControlOwnerPollMS` while a key is held (a hung message loop in the input dependency, a blocked `GetMessage`), the session loop treats it as the key device lost: the gate shuts, the state shows `ptt: lost` with `ptt_problem: read_failed` (the existing vocabulary: "why the key device is not being read", [pkg/schema/voice_control.go](../../pkg/schema/voice_control.go)), and presses are refused until the thread reports again. A watchdog tick from the input thread, consumed by the session loop, is how the stall is noticed; no new state or reason is needed.
- **Device removal is a release.** `RIDEV_DEVNOTIFY` delivers `WM_INPUT_DEVICE_CHANGE` with `GIDC_REMOVAL` ([Raw Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input) describes device-change delivery; the constant is from memory). A removal while a key is held on that device shuts the gate as `key_device_lost` does on Linux; the state shows `ptt: lost` until a device is present again, and every press is refused meanwhile. Unlike Linux, there is no single configured device: the binding applies to every keyboard (or mouse), so `lost` means no device of that class is attached.
- **Missed releases.** A release can be missed when input goes to another desktop (the UAC prompt, the lock screen, Ctrl+Alt+Del) or when a higher-integrity window takes the foreground, if Raw Input is not delivered there (§5). Three things bound the damage: `max_transmit_secs` (default 120, at most 600) ends any single press; the owner sends `set_mute true` on `powerMonitor`'s `lock-screen` and `leave` on `suspend`, both of which Electron documents for Windows ([powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor)); and the state carries `transmitting: true` the whole time, so the tray and window show it. Whether a `BREAK` that happened on the secure desktop is delivered afterwards is E8; if it is not, the helper's own observation of a resync is impossible from safe code (`GetAsyncKeyState` is FFI), and the three bounds above are the answer. #773's rule holds: after lock or suspend, transmission needs a fresh press and, after `set_mute`, a deliberate unmute.
- **Focus changes alone do nothing.** Holding the key across Alt-Tab keeps transmitting; a focus change neither opens nor shuts the gate. Raw Input is not affected by which window is foreground (above), which is the point.
- **Nothing but the bound transitions leaves the input module.** As on Linux: the module yields `KeyEvent` (talk, mute or deafen went down or up) and `DeviceState`, never a scan code, never a count, never a time; Raw Input delivers the whole keyboard stream to the registered window, so the same keylogger-shaped warning the Linux README gives applies, in a milder form (no exclusive grab, no cross-session reach: Raw Input is per desktop session).

### 4.5 Configuration

`voice.toml` `[keys]` on Windows names bindings by scan code and by mouse button, not by device path: `talk = "sc:0x29"` (grave), `talk = "mouse:4"`, with the `E0` prefix as `sc:0xE0,0x1D`. The exact grammar is #777's; the rule is that it is a closed, parseable form that `conch-voice config set` writes and that never names a path. **Binding capture for the UI** happens in the Electron window during configuration, which has focus then: the renderer reads `KeyboardEvent.code` and `MouseEvent.button` (DOM button 3 and 4 are Mouse 4 and 5) and the shell translates to the `[keys]` form and writes it with `config set`. The helper is not involved and no raw input leaves it. The `conch-voice keys` terminal command is Linux-only; a Windows equivalent that prints scan codes to a terminal may be added for diagnostics but is not needed for the product. **Rebinding during a session** restarts the helper (`leave`, `join`) in the first version; a `set_keys` command would be a `conch.voice_control.v3` matter and is not proposed now (§6).

**Platform-neutral.** The push-to-talk machine, the `KeyEvent`/`DeviceState` vocabulary, `ptt`/`ptt_problem` in the state, the release tail and `max_transmit_secs`.

**Open questions.** E7 (winit or alternative: press and release of a key and of Mouse 4 in the background, in a windowed, borderless and exclusive-fullscreen game, with a second listener confirming; repeats; start with the key held; hold past `max_transmit_secs` then reopen; device unplug while held; the dependency audit of §4.3), E8 (secure desktop and elevated foreground), E9 (anti-cheat titles). **Follow-up:** F6, F7.

## 5. Privilege and security boundaries

**Decision proposed.** The app and the helper run as the signed-in user at medium integrity, with no driver, no service, no hook, no injection, no elevation prompt and no instruction to disable protection. Where Windows does not deliver input to a medium-integrity process, the client says so and does not work around it.

- **Elevated foreground.** Windows' integrity mechanism gives "elevated users ... high" and standard processes medium ([Mandatory Integrity Control](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)). User Interface Privilege Isolation blocks lower-integrity processes from sending messages to and hooking higher-integrity windows (memory; the MIC page read for this note does not spell the UIPI list out). **Whether Raw Input registered with `RIDEV_INPUTSINK` is delivered while an elevated game is foreground is not stated on the pages read, and is E8.** If it is not, the capability matrix marks "PTT with an elevated game in the foreground" **unsupported** and the client's diagnostics say "this game runs as administrator; Conch does not, and cannot see your key while it has focus." Running Conch elevated is not offered.
- **Secure desktop.** The UAC prompt, the lock screen and Ctrl+Alt+Del switch to a desktop where ordinary applications have no windows; no input reaches the helper while it is shown. A press that began before the switch may have its release there (§4.4). Lock is observed by the owner through `powerMonitor`'s `lock-screen` ([powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor)); the helper itself would need `WTSRegisterSessionNotification` and `WM_WTSSESSION_CHANGE` ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsregistersessionnotification)), which is Win32 and is only reachable through whichever input dependency §4.3 settles on.
- **Anti-cheat.** Raw Input registration is a passive, documented, user-mode API with no hook, no DLL and no handle into the game. That is the strongest statement that can be made from documentation. Whether a given anti-cheat system tolerates a background raw-input listener is a property of that system and that title, is not documented by vendors, and is **E9 per title**, recorded with versions; the matrix has one row per tested title and no general claim. Hooks (§4.2) would have made this worse, which is one more reason they were not chosen.
- **Microphone privacy toggle.** §2.2.
- **No listener, no secrets in argv.** §3.3–§3.5.
- **The renderer.** Context isolation, sandbox, no Node integration, validated IPC: #770's rules, unchanged on Windows; W5 verifies them on Windows (#779). The helper is started only from the main process.

**Open questions.** E8, E9. **Follow-up:** none beyond W3/W6 acceptance.

## 6. Where input lives

**Decision proposed.** **Input lives in the helper**, on Windows as on Linux. No command of `conch.voice_control.v1` or `v2` presses or releases, and none is added. The invariant, stated as both versions have it: **no control command opens the gate.** In push-to-talk mode the gate is opened by a fresh press and by nothing else; in open mode (`conch.voice_control.v2`, `set_talk_mode open`) it is opened by a fresh onset of the microphone's own sound and by nothing else; `set_talk_mode` only chooses which of the two may open it, and mute and deafen shut it in both ([conch-voice.md §3](conch-voice.md) as amended for v2; [tui-voice.md §20.6](tui-voice.md); [pkg/schema/voice_control_v2.go](../../pkg/schema/voice_control_v2.go)). The v1 comment "the gate is opened by a press and by nothing else" ([pkg/schema/voice_control.go](../../pkg/schema/voice_control.go)) describes v1's single mode, not v2. Windows changes where the press comes from and nothing about the onset. Bindings are configuration (`voice.toml [keys]`, written by `config set`), not protocol. **No versioned control extension is needed for input in the proposed design.**

Why this is the right place: the gate is in the helper, next to the capture ring; a press that travelled from another process would add a hop and a channel that could be driven by anything that can write to it. The Linux design chose this for the same reason, and the Windows backend changes only where the press comes from.

When a control extension **would** be needed, so that nobody adds it by accident:

- if #769 chooses model C of §7 (Chromium owns the microphone, the helper is reduced to an input source), presses must cross a channel to the shell. That is a **new** versioned shape, `conch.voice_input.v1` (helper → shell, `pressed`/`released` with no key identity), not a repurposed v1/v2 command, and the gate it drives is the browser one (`web/src/voice/gate.ts`) with its own fail-closed rules;
- live rebinding (`set_keys`) or reporting which binding is in force would be `conch.voice_control.v3`, with the hello negotiation of §20.2 of tui-voice.md. Not proposed now (§4.5).

The desktop shell needs no helper change to show binding state: `ptt` (`ready`, `not_configured`, `lost`, `unknown`) and `ptt_problem` are already in every state.

## 7. Native voice plus screen capture, with #769

**Decision proposed, for #769 to confirm:** **Model B.** (*Reconciled 2026-10-28:* the Linux design, [linux-desktop.md §6](linux-desktop.md), proposes the same model for both platforms, keeps the helper-only bridge as the considered alternative, and carries the shared transport, input and lifecycle contracts; where the two documents differ, the Linux document is the later word and this one follows it.) The Rust helper is the person's one LiveKit participant for voice (publishes the microphone, plays remote voice). Screen video is captured and published by Electron (Chromium's `desktopCapturer` and the LiveKit JS SDK) as a **companion participant that conchd sanctions**: a second, short-lived grant tied to the voice session, under a different LiveKit identity that conchd derives from the person's and recognises as the same person, with publishing limited to screen video and the scoped audio of §8, folded out of occupancy and presence by conchd, and ended when the voice session ends. One microphone publisher, one voice playback path: the companion publishes no microphone, and what it **subscribes** to is governed as §7.2 says, because LiveKit's grant cannot say "video only".

**What LiveKit's grant can and cannot express** ([`auth/grants.go`](https://raw.githubusercontent.com/livekit/protocol/main/auth/grants.go)): `canPublish` and `canSubscribe` are each a single `*bool`; `canPublishSources` ("TrackSource types that a participant may publish") restricts **publishing** by source (camera, microphone, screen share, screen-share audio); **no field restricts what may be subscribed**, by kind or source; `hidden` makes a participant invisible to others. So a server-enforced companion is either **publish-only** (`canSubscribe: false`, `canPublishSources: [screen_share, screen_share_audio]`), which cannot watch a share, or **subscribe-all**, which can also receive the room's voice and would play it a second time unless the client refrains. The first draft of this note claimed a video-only subscribe grant; there is none.

### 7.1 Why a decision is needed at all

Today one person is one LiveKit participant: conchd derives the identity from the principal (`voiceIdentity(p.ID)` in `internal/server/voice.go`) and signs a grant for it. Two facts, kept apart because the first draft ran them together:

- **conchd does not refuse a second session for the same identity.** `voiceSession` records the credential as a holder of the room and signs a token on every request; `TestVoiceSessionRecordsTheHolder` in `internal/server/voice_test.go` expects 200 for "the same session again". Grant issuance is unlimited per person.
- **LiveKit disconnects the earlier connection when the same identity connects again.** The helper maps the SDK's `DUPLICATE_IDENTITY` disconnect reason to `duplicate_identity` (`voice/conch-voice/src/livekit.rs`, `sdk.rs`: "the same identity joined from elsewhere"); the fixture `event-state-failed-duplicate-identity.json` is that outcome. The displacement rule itself is LiveKit's (memory of its server behaviour; E10 records it).

So today a second client holding the person's credential can take a token and **displace** the first at LiveKit; that is existing behaviour, not something this design introduces. A desktop app whose voice is in the helper and whose screen is in Chromium would be exactly that: two connections for one identity, the second displacing the first. Watching a share also needs a participant, so the problem is not only publishing.

## 8. Application audio vs loopback

**Decision proposed.** Three audio scopes for a share, each named truthfully, **off by default**:

| Scope | Mechanism | Rebroadcasts the call? | Status |
| --- | --- | --- | --- |
| none | — | no | default |
| **this application** | process-tree loopback: `ActivateAudioInterfaceAsync` with `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, include the picked window's process tree; "only audio from the specified process, and its children, will be captured"; "requires Windows 10 build 20348 or later" ([ApplicationLoopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), page dated 2026-02-19). Natively, through the `wasapi` crate if E5 confirms it exposes the include/exclude modes | **no, on one condition:** the picked window's process tree must not contain the process that plays the call. If the person picks **Conch's own window**, the tree is Electron's, and the helper is Electron's child, so include-tree capture of it would carry the room's voices back into the room. Rule: the shell resolves the picked window to its root process and **refuses application audio when that tree contains the helper's pid or the shell's own**, offering the picture alone and saying why; the same refusal applies to any other window whose tree the helper has been placed in. The rule is checked by pid, not by window title | pending E5 (which must include sharing Conch's own window while receiving voice, with application audio requested, and show that nothing of the call is captured) |
| **everything but the call** | the same API with the **exclude** mode on our own process tree (the helper and the Electron tree): "capturing all system audio except those from the specified process (and its children)" (same page) | no, by construction | pending E5 |
| whole output through Chromium | Electron's `setDisplayMediaRequestHandler` with `audio: 'loopback'` or `'loopbackWithMute'`: "will capture system audio, and is currently only supported on Windows" ([session](https://www.electronjs.org/docs/latest/api/session)); `loopbackWithMute` is listed and not defined on that page (memory: it mutes local playback of what is captured) | **yes**: endpoint loopback captures the helper's playback, so the room hears itself | **not offered** as "system audio"; at most an explicit "share everything including this call's voices" with a warning, if W4 wants it |

Per-window audio in Chromium's `getDisplayMedia` (the `windowAudio` hint) was a specification proposal in June 2025 ([W3C webapps list](https://lists.w3.org/Archives/Public/public-webapps-github/2025Jun/0114.html); [Screen Capture draft](https://www.w3.org/TR/2026/WD-screen-capture-20260716/)); whether the pinned Chromium ships it was not established here and is E5's last item. If it does, it is the simplest route for "this application" under model B, because the companion already publishes the video.

Under model B, scoped audio captured natively by the helper would be a second audio track that has to reach the same share the companion publishes; that plumbing (helper track to the companion's participant, or the helper publishing a `screen_share_audio` track on its own participant that viewers associate through presence) is W4's design and not decided here. **Feedback avoidance** is structural, not a filter: only the two process-loopback modes are offered as application or system audio, the exclude mode leaves the call's playback out by construction, and the include mode is refused for any process tree that contains the playback process (table above). **Unsupported fallback:** when process loopback is unavailable (older build, the API refusing, the picked source having no audio session: "the capturing process receives silence", same sample page), the picker says "sound from this application is not available here" and shares the picture; it never widens to the whole output on its own. Source closure, minimised windows, exclusive fullscreen, protected content, multi-monitor and DPI changes are capture-side facts for W4 to record per configuration (E11), with "unsupported" as an allowed answer.

**Platform-neutral.** The three-scope vocabulary and the off-by-default rule, which Linux (PipeWire application streams) and macOS can implement by their own means. **Open questions.** E5, E11. **Follow-up:** W4 itself (#778); F9 if a schema is needed for the audio scope in share claims.

## 9. Credentials, lifecycle, installer, signing and updates

### 9.1 Credentials

**Decision proposed.** The shell keeps each server profile's token with Electron's `safeStorage`, whose Windows keys "are generated via DPAPI" and protect content from other users "but not from other apps running in the same userspace" ([safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)). That is stated to the user in those words. The asynchronous API is used (`isAsyncEncryptionAvailable()`; the synchronous API "will be removed in Electron 46"). If encryption is unavailable, the profile offers **session-only login** and says why; nothing plaintext-equivalent is persisted. The token reaches the helper as `CONCH_TOKEN` with `credential: env`, in a child environment built from empty by a case-insensitive allowlist (§3.7), and is never in argv, logs or the renderer's storage. Per-profile isolation, logout clearing, late-response fencing and no credential transfer on redirect are #770's rules; W5 (#779) verifies them on Windows.

### 9.2 Lifecycle

Close quits and stops media by default; close-to-tray is explicit opt-in with a visible, truthful tray state and a Quit; no hidden session if the tray is unavailable (#773). On `lock-screen` the owner sends `set_mute true`; on `suspend`, `leave`; on `resume`/`unlock-screen` nothing joins or unmutes by itself ([powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor): both events on Windows). Startup launch is off by default and never joins voice. Single instance through `app.requestSingleInstanceLock()`, with the lock scoped so that an isolated test instance (a different `userData`) does not collide ([launch from URL](https://www.electronjs.org/docs/latest/tutorial/launch-app-from-url-in-another-app)). Invite links: `app.setAsDefaultProtocolClient` for the documented scheme, the URL arriving as the last element of `commandLine` in `second-instance` or in `process.argv` on a cold start (same page); it is parsed strictly, shows the destination server, requires a click to join, never joins voice, and is never logged whole. A stable `AppUserModelID` set with `app.setAppUserModelId` and matched by the installer's shortcut, which Windows notifications and taskbar pinning require ([notifications](https://www.electronjs.org/docs/latest/tutorial/notifications); [autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater)).

### 9.3 Installer

**Decision proposed.** One **per-user installer** that needs no administrator, built by **electron-builder's NSIS target** (assisted, not one-click; per-user; no elevation), bundling `conch-voice.exe` beside the app. **From memory, not re-verified** (the electron-builder site returned nothing to this session twice): its NSIS defaults are `oneClick: true` and `perMachine: false`, so the per-user mode is the default and `oneClick` is what to turn off. Confirmed at #780 before anything is pinned.

### 9.4 Signing

Windows "requires software to be signed with an 'extended validation' certificate" for the warnings to go away, EV keys must live in hardware or a cloud signer, and **Azure Artifact Signing** (renamed from Trusted Signing) is "the cheapest option" but "currently limited to developers in certain countries" ([Electron code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing); [Artifact Signing overview](https://learn.microsoft.com/en-us/azure/artifact-signing/overview), which describes Basic and Premium SKUs and identity validation but states no eligibility or pricing on that page). Electron's page says Artifact Signing "gets rid of SmartScreen warnings"; Microsoft's own overview makes no SmartScreen statement, and #756 is right that signing is not a reputation guarantee. **For the owner to decide:** which signer (Artifact Signing, if eligible as an individual in his country; else an EV certificate with a cloud HSM such as DigiCert KeyLocker), its yearly cost, and the account it lives in. Everything shipped is signed: installer, uninstaller, the app executable, and `conch-voice.exe`. Unsigned private previews are labelled as such and never come with instructions to disable SmartScreen or antivirus.

### 9.5 Updates

First version: **manual, verified.** The app checks the release feed, shows the new version, and opens the signed installer's download in the browser; it verifies nothing weaker than the signature and a published SHA-256; it never restarts during a call; the helper's hello and the shell's version check guard a mismatch. Automatic updates are deferred by #756; when wanted, the choice of §9.3 decides the mechanism.

**Platform-neutral.** Profiles, isolation, lifecycle states, invite-link rules, version display: #770/#773. **Open questions.** E12 (clean-machine install, upgrade, uninstall, two profiles), the owner's signing decision. **Follow-up:** F11, F12.

## 10. What stays unchanged on Linux

- `dmn-audio`, evdev key reading, fd 3, process groups, `SIGTERM`: all kept, all behind `cfg(target_os = "linux")` where a Windows counterpart exists.
- `voice/Cargo.toml`: `unsafe_code = "forbid"` on every crate; `unwrap_used`/`expect_used` denied.
- Every golden fixture under `pkg/schema/testdata/voice-control*` byte-identical; `scripts/schema-compat.sh` unchanged in what it checks.
- `make check`'s Rust leg runs on Linux as today; Windows builds and tests are a separate CI job on a Windows runner (F1), never a gate on Linux work.
- `conch` (the TUI) does not gain Windows voice in this epic; the Windows transport does not preclude it (a Go owner can create a named pipe through `golang.org/x/sys/windows`, already an indirect module, and could add the DACL and client-pid check of §3.5).

## 11. Proposed amendment to ADR-006 (not an edit; for the owner)

> **Platform (amended):** Linux with PipeWire, through `dmn-audio`; and Windows 11 x64 with WASAPI, through the `wasapi` crate, and Raw Input through [the crate §4.3 settles on], each behind `cfg(target_os)`. The audio and key-source layers are the only platform-specific code; the gate, mixer, session loop and control protocol are shared. Other platforms still need a decision of their own.
>
> **Dependencies (amended):** the allowlist gains `wasapi` and [the input crate], Windows-only. `scripts/voice-pins.sh` pins the Windows libwebrtc archive by hash as it pins the Linux one. `deny.toml` checks both targets.
>
> **Consequence added:** CI gains a Windows job for `voice/`; the Linux leg of `make check` is unchanged.
>
> **Transport on Windows:** commands on standard input, the only channel that carries authority; events on an owner-created named pipe whose DACL is the cross-user boundary; a one-line attach (`conch.voice_control_pipe.v1`) binds the connection to the spawned process as defence in depth. It is not authentication of either side, and same-user code is outside the model, as it is on Linux.

If route 3 of §4.3 is taken, the amendment also names the one crate allowed `unsafe` and the review rule for it, and CLAUDE.md rule 6 changes with it. Written here as text for Nick to accept, reject or edit; ADR-006 itself is untouched by this PR.
