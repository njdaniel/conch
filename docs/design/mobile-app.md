A member opens an invite on their phone, confirms which server it names, signs in, reads and writes in the channels they belong to, sends a picture, joins voice when they choose, keeps the call through a screen lock and an app switch, comes back to find nothing transmitting that they did not press, leaves, and signs out. ### 1.2 Transport assumptions the phone inherits

Verified in `web/src/platform/browser/http.ts`, `web/src/api.ts`, `web/src/state/feed.ts`, `internal/server/ws.go`, `internal/server/voice_ws.go`:

- **Bearer in the `Authorization` header, never in a URL, log, or the DOM** (`api.ts` header comment); every browser fetch sends `credentials: 'omit'` and `cache: 'no-store'`: no cookies anywhere. A phone client keeps exactly this: one bearer per device credential, in the platform keystore (§8), sent as a header.
- **A WebSocket is opened with a single-use ticket** in the query, obtained by `POST /v1/ws-tickets` just before each socket; the desktop's `SocketTransport.ticket` flag records the only alternative (main opens the socket with the bearer itself). A phone client is a native HTTP client and may do either; the ticket path is what the server exposes to any client and is proposed, because it keeps the bearer out of the upgrade request's query and proxy logs.
- **Feed liveness is the client's job:** heartbeat frames, a 60 s silence timeout, backoff from 1 s to 30 s (`feed.ts`: `silenceTimeout`, `firstDelay`, `maxDelay`), close code 1008 as policy (`policyClose`). The server re-checks the credential on an open socket every 30 s (`defaultCredentialRecheckInterval`, `ws.go` line 32) and closes it at once when the principal is removed, disabled or signed out or the credential is revoked (`voice_ws.go` header comment). A phone whose socket dies in the background must therefore expect to re-ticket and reconnect on resume. **A policy close is not, by itself, a sign-out:** the server closes with 1008 for three causes: the channel's membership lost, a reader too slow to keep up, and a revoked credential (`SocketCloseRevoked` with `StatusPolicyViolation`, `internal/server/ws.go` lines 537 and 556), and `feed.ts` maps all of them to `denied`, keeping `unauthorized` for a ticket refused with 401 (lines 56–59, 169–188). The close code alone cannot tell the three apart, which is why the phone **revalidates** rather than guesses: after the revoked case `whoami` answers 401 and that is the confirmation. The phone follows the same split: on `denied` it revalidates (`whoami`, then the channel list) and drops that channel's feed if the channel is gone, keeping the credential; it forgets the credential and shows signed out **only on a confirmed authentication loss**: a 401 from the ticket route or from `whoami`, as `authReducer`'s `unauthorized` does, and as §3.5's rows say.
- **A voice join token lives 15 s** (`voiceTokenLifetime`, `voice.go` line 29; LiveKit adds 60 s of leeway, so about 75 s to connect). The session response names the LiveKit URL, the person's identity `p<id>` and `companion_identity` `p<id>.screen` (`voiceSession`, `voice.go` lines 281–293). A phone that is suspended between asking for a session and connecting must ask again, never cache a token.
- **The server reads no client address**, neither `RemoteAddr` nor `X-Forwarded-For` (ADR-008 consequences); nothing on the phone may depend on it.
- **One origin per server profile.** The browser is served from its server and reaches only `'self'` plus the LiveKit origin (`webCSP`, `internal/server/static.go` line 30; the `connect-src` rewrite at line 71). A native app has no CSP; §8 says what replaces it (an allowlist of exactly two origins per profile: the server and the LiveKit URL the session names).

### 1.3 The generated schema

`web/src/schema/generated.ts` is written by `go generate ./pkg/schema` from the tables in `pkg/schema/ts.go` (238 exported interfaces and types at the baseline, counted by `grep -c '^export (interface|type)'`), each with a validator built from the combinators in `web/src/schema/validate.ts` (`str`, `int`, `bool`, `timestamp`, `json`, `vocab`, `array`, `optional`, `object`, `tagged`). `generated.families.ts` maps each golden-fixture family in `pkg/schema/testdata/` to its validator and `schema.test.ts` checks every fixture against it. `scripts/schema-ts-check.sh` fails `make check` when the file is stale or edited.

What this means for a phone client, in order of how little it adds:

1. **A React Native client imports `web/src/schema/` as it stands.** `validate.ts` and `generated.ts` use no DOM, no `window` and no React: verified by reading `validate.ts` and the head of `generated.ts`. The same generator, the same fixtures, the same check. No new generator and no change to `pkg/schema/ts.go` is needed for the experiments; M6 decides whether `mobile/` consumes the file in place (a workspace path) or the generator writes a second copy (a table change under `schema-change`).
2. **A Kotlin and a Swift client need a second and a third emitter** from the same `ts.go` tables (or from the Go types directly), each with its own fixture conformance test, as the Rust client has (ADR-006: "its wire types are checked in CI against the golden fixtures"). That is new generator work under the protocol designer and a `schema-change` review, before any screen is written.

Unknown-field tolerance holds either way: `object()` in `validate.ts` reads the fields it names and ignores the rest (source-inspected), which is what lets a phone built against this commit keep working as additive fields land (ADR-013's I1 adds several; ADR-015 added `VoiceParticipant.camera`).

## 2. The stack: four options compared

The comparison is written for the story in the preamble, with the voice lifecycle as the deciding axis, because text chat works on every option and voice-in-the-background works on few. Each cell says whether the claim is verified-by-docs (a cited page, §12, read 2026-11-01), source-inspected (this repository), from memory, or pending (M4 or M5).

| Axis | **PWA** (today's React client, added to the Home Screen) | **Native wrapper** (the React client in a WebView: Capacitor) | **React Native** (shared TypeScript logic, native views, LiveKit RN SDK) | **Separate Kotlin and Swift clients** (LiveKit Android and Swift SDKs) |
| --- | --- | --- | --- | --- |
| Background audio while in voice | **Not promised and not designed for.** The page shuts the gate on `blur`, `pagehide` and `visibilitychange` (source-inspected, `useVoice.ts`) and says so ("the talk key and hold-to-talk work only while the page is active", mobile-browser-layout §6). Whether a backgrounded or locked phone browser keeps the WebRTC connection and playback at all is **not established by any page read** (the Chrome and WebKit searches found no authoritative statement) and is a pending row (M-L1 in the report) | A WebView is the same engine with the same background rules; Capacitor's own pages say nothing about background audio or WebRTC in WebViews (read: docs home, iOS and Android pages). What it adds is the host app's ability to declare `UIBackgroundModes` and run an Android foreground service, which the WebView's capture would then have to survive: **pending, and the least documented of the four** | The SDK's README names the mechanism on each OS: Android "To support staying connected to LiveKit in the background, you will need a foreground service" with `FOREGROUND_SERVICE_MICROPHONE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`; iOS "simple background processing can be enabled by selecting the `audio` and `voip` UIBackgroundModes", which "will keep the app alive in the background as long as a mic or audio track is playing", with CallKit recommended for "a more robust background" (verified-by-docs, `client-sdk-react-native` README). Nothing stands between the app and the OS: the most controllable, and **pending** on the same rows |
| Audio routing (earpiece, speaker, Bluetooth, interruptions) | Whatever the browser does; a page cannot choose an output on iOS (`setSinkId` absent; from memory) and cannot see a phone-call interruption as such | The WebView's routing, plus whatever native plugin is written; no plugin is in Capacitor core for this (not found in the pages read) | iOS: `registerGlobals()` configures `AVAudioSession` and the default `playAndRecord` options include `allowBluetooth` (verified-by-docs, README and release 3.0.0); Android: `AudioType.CommunicationAudioType` by default and `manageAudioFocus: true` in the README's example (verified-by-docs). ### 2.1 Recommendation

**Run M4 and M5 on React Native with the LiveKit React Native SDK, bare (no Expo Go), with the Kotlin-and-Swift pair as the fallback that M6 may still choose.** The reasons, and what would change the answer:

1. The PWA is already shipped and is the no-install path for every phone (ADR-008). It is kept and improved by the browser track; it is not the phone app, because nothing in the browser lets the app own the audio session, the foreground service or the lock-screen behaviour #757 asks for, and the pages read give no footing to promise background voice from a page. If M-L1 (the report's "what does a locked phone browser do") unexpectedly passes on both OSes, the phone app's priority drops and Nick should hear that before M6.
2. The WebView wrapper buys the native shell without the native media stack: capture and playback stay in the WebView, where the same unknowns apply and where the project's own voice code (`sdk.ts`) would run under a WebView's permission model. It is the least documented path of the four and it is not recommended for the experiment.
3. React Native reuses the modules that carry Conch's protocol discipline (the operation table, the generated validators, the chat reducer, the feed machine, the transmit gate, the disconnect table) and rewrites only views, which the phone needs rewritten anyway (M2). Its LiveKit SDK documents the OS mechanisms this note needs and it ships the same `livekit-client` core the browser uses, so the server's rules (15 s tokens, `p<id>` identities, transmit reports) are met by code the project already reads. The cost is a third runtime (Hermes; from memory) and a dependency surface M4 and M5 must inventory before anyone pins it.
4. Kotlin and Swift are the most controllable and the most expensive: two codebases, two schema emitters, two sets of gates. They are the right answer **if** M4 or M5 finds that the shared layer cannot do something the OS requires at the right moment (an audio-session change inside an interruption callback, a foreground service started from exactly the user action the OS demands) and the LiveKit RN SDK offers no hook for it. The experiments are written so that either lane can be swapped to its native SDK with the same matrix.

**What this recommendation is not:** the production stack. #757 puts that at M6, after both real-device receipts, and ADR-016 says so in its status.

## 3. One media owner, identity, hand-off and removal

### 3.1 Identity, in the server's terms

Verified in `internal/server/voice.go`, `voice_presence.go`, `voice_companion.go` and `voice_ws.go` at the baseline:

- A **principal** is a person (or agent). A principal holds many **credentials**; each sign-in (a password login, a redeemed invite, a redeemed sign-in link) makes one, listed by `GET /v1/credentials/mine` with a `label` and ended by `DELETE /v1/credentials/mine/{id}` from any device, or all at once by `revoke-all`. There is **no device entity**: a device is the credential it holds, and the server knows nothing else about it.
- A **voice session** is the record that a credential holds a room (`voiceSession` records the holder and signs a token, `voice.go` lines 281 onward). conchd **does not refuse a second session for the same person**: `TestVoiceSessionRecordsTheHolder` expects 200 for "the same session again" (linux-desktop §1, re-read at this commit). The limit on one person's connections is **LiveKit's identity rule**: a second connection as `p<id>` displaces the first with `DUPLICATE_IDENTITY`, measured at 507 ms once on real LiveKit 1.13.7 (the Linux report's F1, synthetic, n = 1).
- The **participant identity** is `p<id>` for the person, `p<id>.screen` for the desktop's screen companion and `p<id>.view` for a viewer; `parseVoiceParticipant` accepts nothing else and a client never chooses a suffix (voice-control-plane §13; `voice_presence.go` line 474). Presence folds the suffixed identities into the person: one `VoiceParticipant` per principal, so a phone reading `GET /v1/channels/{channel}/voice` can see **its own principal already present** when another device is in the room. That is the signal §3.2 uses.
- **The browser already stops on displacement:** `afterDisconnect('duplicate_identity')` is `stop`, "Another device took over your place in this voice room" (`web/src/voice/disconnect.ts` line 24), and conch-voice.md §5's table says the same for the helper. No device reconnects into a displacement loop today.

### 3.2 The policy proposed: one voice participant per person per room, moved by the person

**Authoritative owner, per room:** the person's `p<id>` connection in a given room, on whichever device holds it. There is exactly one per room at a time. This is what the server enforces today through LiveKit (`voiceIdentity`: "one principal, one connection per room"; displacement is LiveKit's identity rule inside one room), and this note proposes to **keep displacement as the mechanism and make it an explicit act**, not to add a server rule:

1. Before the phone joins, it reads presence. If its own principal is listed, the Join control says so in words M2 chooses, to the effect of "You are in this voice room on another device. Joining here moves voice to this phone." Join is still one press, but it is a press that was told.
2. The phone asks for a session and connects. LiveKit displaces the other device; that device's existing rule (`stop`, never rejoin) applies; its UI says voice moved. Nothing on the server changes.
3. The reverse hand-off is the same gesture from the desktop or browser, which already behave this way without the warning; adding the same presence check and words there is a small browser and desktop follow-up (§10), not a prerequisite.
4. **No simultaneous voice devices in one room.** Two microphones for one person is not a feature anyone asked for, and listening on two devices at once is not available today for a person's own identity in one room. If Nick wants "my phone listens while my desktop talks" later, that is a new server design (a listen-only second identity for the person, distinct from the desktop's `.view`, which is tied to the same machine's share-watching) and a wire change; it is listed in §10 as a question, not proposed.
5. **Across rooms the enforcement does not reach, and this note does not pretend it does.** Rooms are per channel (ADR-005; `ChannelVoiceRoom`). A person whose desktop is in channel A's voice can join channel B's voice from the phone: both connections stand, both may transmit, and nothing on the server or in LiveKit relates them. Today the browser's UI keeps one page in one room at a time, but two devices are two pages. The phone cannot even warn cheaply: `GET /v1/voice/occupancy` gives per-channel counts only (`VoiceChannelOccupancy` is `{channel_id, in_voice}`), so finding "am I in voice somewhere else" means a presence read per channel the person belongs to. **Two honest options, for Nick:** (a) accept the per-room scope for the alpha and let the phone warn only when it can see itself in the room it is about to join (this note's proposal); (b) a **global owner**: conchd ends the person's other-room session (or refuses the new one) when it issues a session for a different room, and tells the person where they are in voice (a field on `whoami` or an occupancy addition). (b) is server work, a wire addition and a behaviour change for the TUI, browser and helper, so it is a future issue (§10) and not something the phone can supply on its own.

**Why not refuse the second session on the server instead** (409 when `p<id>` is already in the room): it would turn the common case, a phone picked up after a desktop was left in voice, into a dead end that needs the other device to leave first, and the desktop designs chose displacement for the same reason (a second companion is refused because a share can be stolen; a second **voice** connection displaces because the person is the same person). The browser's stop-on-displacement already makes the loop safe.

### 3.3 Credential and session identity on the phone

- **One credential per phone install**, made by the sign-in the person chose: a redeemed invite, a password, or a one-use sign-in link made on another device (§1.1). It is stored in the platform keystore (§8), never exported, and is what the phone presents as `Authorization: Bearer`.
- **Its label is what the person sees in "My sign-ins" everywhere.** `OwnCredentialV1.label` exists. Verified in `generated.ts`: `LoginRequestV1` is `{name, password}`, `RedeemInviteRequestV2` is `{code, name, password}`, `JoinAccountRequestV1` is `{name, password}` and `RedeemSignInLinkRequestV1` is `{code}`: **none lets the signing-in client name its credential.** `CreateDeviceLinkRequestV1` has an optional `label`, set by the **maker** of the one-use link (the desktop that says "my phone" before showing the code). So the sign-in-link path already yields a labelled phone credential, and the password and invite paths yield whatever the server chooses today (not verified which; M7 reads it). A client-side device label for those two routes would be an **additive request field**, named in §10 as a future schema issue; the experiments do not need it.
- **Server profiles** are the desktop's concept (linux-desktop §4): a random local id bound to a canonical origin and a verified principal, never keyed by hostname. The phone keeps the same model, one credential per profile, and switches profiles by tearing media down first and fencing every async completion by a generation, as the desktop specifies. Nothing here needs a wire change.
- **A voice session on the phone is a credential's session.** When the credential is revoked (`DELETE /v1/credentials/mine/{id}` from the desktop, `revoke-all`, an operator's revoke), the voice socket closes within the 30 s recheck, the next session request answers 401, and the poller evicts the participant on entitlement loss (`voiceStillEntitled`; linux-desktop §6.4 "entitlement loss removes both the person and the companion"). The phone treats any of these as **sign-out with media torn down**, as `authReducer`'s `unauthorized` does, and never retries a session with a dead credential.

### 3.4 Companion and viewer identities are not phone authorisation

`p<id>.screen` and `p<id>.view` exist so that **one machine** can hold voice in the Rust helper and screen media in Chromium (model B, accepted 2026-10-28). The route issues `.screen` only when `p<id>` is already in the room and refuses a second (409 `voice_companion_busy`); it issues `.view` to anyone with a live entitlement and a room someone holds, and a second viewer displaces the first (voice-control-plane §13). A phone must **never** ask for either as a way to be in a room beside the person's other device:

- not `.view` to "listen along": it was designed as the same person's second window on the same desk, it hears the whole room, it is folded into the person in presence, and using it from a second device would be exactly the simultaneous-device behaviour §3.2 does not propose, reached through a side door;
- not `.screen` for anything: a phone does not share its screen (§8).

A phone that watches a share does so **as `p<id>` in watch-only mode**, the browser's path, which means it holds the person's place and displaces a desktop in voice. That is the hand-off of §3.2 again, and the phone's Watch control says so in the same words. If that is too blunt for daily use, the answer is the §10 question, decided by Nick, not a phone-side use of the viewer identity.

## 4. Transmit behaviour: foreground PTT and the open microphone

The object is the gate of `web/src/voice/gate.ts` and conch-voice.md §3: **microphone audio leaves the device only while the gate is open; a press opens it in push-to-talk, an onset in open mode, and nothing else: no command, timer, reconnection, resume or cleared condition.** The phone inherits the rule and the browser's gate, and **adds two things the browser's gate does not have** (§1.4): a **lifecycle block** that shuts the gate in **both** modes on background, lock and interruption (the browser's `lost()` shuts push-to-talk only), and a **resume latch** that, after any unblock, requires quiet for the hang time and then a fresh onset before open mode may open (the browser's gate opens on the first loud sample after `setBlocked(false)`). Both are **new work** for M4 and M5, measured by rows M-L8 and M-L9, not reuse. The helper has both already (conch-voice.md §3: the detector starts *sounding* and every shut reason applies in open mode); the phone copies the helper's semantics into the browser's gate.

The publication order is the browser's, fixed by #501 and kept: **the track is muted before it is published, and the publication is muted again after publishing and after any republish** (`web/src/voice/sdk.ts` lines 634–645: "published unmuted and muted after, it was listed unmuted for about 5 ms of every join ... a pass of conchd's poller landing there recorded a transmission nobody had made"). Row M-F7 checks that joining without a press sends nothing.

### 4.1 Foreground push-to-talk

| Moment | Behaviour | Source of the rule |
| --- | --- | --- |
| Touch down on Hold to talk | `press()`: report `started`, wait for the answer or the bounded wait, unmute | `connection.ts` header (#495, #965): the page says transmitting only once the track is unmuted |

| App goes to the background, screen locks, another app takes the foreground | the **lifecycle block**: shut at once with no tail in push-to-talk **and** in open mode (unless the §4.2 opt-in is on and demonstrated), before the OS suspends anything | `useVoice.ts` lines 433–450 (`blur`, `pagehide`, `visibilitychange`) are the browser's push-to-talk-only version; the phone's equivalents are the app-state and lifecycle callbacks, named per OS in the report rows M-L2, M-L3 and M-L8 |

**A lock-screen or notification Hold to talk control is not proposed** in this phase: a press that the app cannot see released (the screen went off mid-press, the notification was dismissed) is the stuck-key case, and neither OS was shown to deliver release events to a backgrounded app for such a control. It stays **unsupported** until a per-OS experiment shows press and release both arrive and the bound still holds (report rows M-H1 to M-H3).

### 4.2 Open microphone

Open mode is level-triggered, never always-on (conch-voice.md §3; `gate.ts` `level()` with `hang`): the gate opens on sound above the threshold and shuts after the hang, every reason that shuts it in push-to-talk shuts it here, and a cleared reason needs a fresh onset. On a phone:

- **In the foreground:** as the browser, with the same warning about speakers until echo cancellation on that device is measured (M-F4); the OS's own processing (`echoCancellation`, `noiseSuppression`, `autoGainControl` as `sdk.ts` sets them) is a device-by-device result.
- **In the background: off by default.** Leaving the app with the microphone open means a device transmitting whatever it hears with the screen dark. The proposal is a per-device setting, "Keep the microphone open in the background", **shown on an OS only after M4 or M5 has demonstrated** that (a) capture continues there, (b) the OS shows a persistent indicator the whole time (Android's foreground-service notification and the status-bar microphone dot; iOS's microphone indicator; both from memory as to their exact form, measured in M-L4), (c) an interruption shuts the gate and the gate stays shut until the person acts, and (d) the battery and data cost over the M-E rows is recorded. Until then, going to the background in open mode runs the **lifecycle block** (new work, §4 preamble: the browser's `lost()` would **not** do this, since it shuts push-to-talk only) and the call stays connected, listen-only, until the person returns. Row M-L8 is the check: sustained sound at the microphone across the background event produces no transmission after it.
- **Resume never unmutes.** The browser's gate opens on the first loud sample once it is unblocked; the phone adds the **resume latch** (new work): after any unblock (return to the foreground, the end of an interruption, a reconnect, a mode change), open mode starts *sounding*, as the helper's detector does (conch-voice.md §3: the first opening always follows quiet and then an onset), so a room that is loud when the app comes back transmits nothing until the sound stops and starts again. The UI says "microphone paused: tap to resume" if the person had muted it or an interruption shut it. There is no path from "the app came back" to "the gate opened". Row M-L9 is the check: sustained sound across the unblock produces no transmission until a quiet-then-onset.

### 4.3 Background connection without transmission

Staying **in** the room while backgrounded or locked, hearing the others, with the gate shut, is the behaviour the story asks for ("keep the supported voice session through app switching/screen lock"). It is the OS mechanism of §2's first row (an Android foreground service of the right types started from the Join press, which is a user action, so it meets the "while the app has a visible activity" rule verified-by-docs; the iOS `audio` background mode while a track plays, verified-by-docs). It is **pending** on both OSes (M-L rows), and the policy if it fails on an OS is honest: the phone leaves voice when it is backgrounded on that OS and says so, as the browser says it today.

### 4.4 What the OS may do that the app cannot prevent

Doze restricts network and CPU for apps that are not in the foreground (verified-by-docs) and the App Standby page says a process "in the foreground, either as an activity or foreground service" is not idle; it does **not** say a foreground service is exempt from Doze (the subagent looked and did not find it). Vendor power managers go further than AOSP ("Android manufacturers listed below prefer battery life over proper functionality of your apps", dontkillmyapp.com, with Samsung, Xiaomi, OnePlus and Huawei scored 5). The report therefore measures M-L rows per device model, and a supported device list names models, not an OS version alone.

## 6. Notifications: what this note fixes and what M3 decides

Fixed here, because they are architecture:

- **No push is required** for anything in the story. Without it the app learns of new messages when it is in the foreground over the feeds it already opens, and of unread counts from `GET /v1/read-state` on launch. "No push" is a supported configuration, not a degraded one, and the alpha record tests it (#757, "push/no-push").
- **Push never joins voice, never unmutes, never opens a session.** A notification tap opens the app on the channel named, after verifying that the credential still works and that the channel is still the person's; a stale tap (the channel gone, the credential revoked) lands on the channel list or the sign-in screen with a line saying why (M7/M12 own the words).
- **A VoIP push is not a chat notification.** It must present a CallKit call or it cannot be used (verified-by-docs, §2); Conch has no incoming call to present. M3 does not use PushKit for messages.
- **Approval notifications stay on ntfy** (ADR-000 D7). Decisions stay out of the phone app in this phase (§8).

Everything else (the registration shape, the provider, what a notification body may carry, the privacy of a self-hosted server talking to a vendor's push service, Web Push versus FCM versus APNs, provider outage) is `docs/design/mobile-notifications.md` (M3, #1108), which brings Nick its own decisions.

## 8. Threats and security review targets

| Threat | Boundary proposed | Verification |
| --- | --- | --- |
| The bearer leaks from the phone (backup, another app, logs, a crash report) | Android: Keystore-backed storage with `allowBackup` off for the credential; iOS: Keychain with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` ("Items with this attribute do not migrate to a new device", verified-by-docs). Never in argv, logs, analytics or the URL (the WS ticket is single-use and is the one query credential, as in the browser) | a receipt that a device backup and restore to a second device yields no sign-in; a log scan in every experiment |
| The phone talks to the wrong server | one profile is one canonical origin, root-mounted HTTPS; plain HTTP only for an explicit development profile on a LAN; **an allowlist of two origins per profile**: the server and the LiveKit URL its session names; no redirects followed on authenticated calls; private-CA servers trust the CA through the OS store, never by disabling validation (the desktop rules of linux-desktop §3) | packaged negative tests in M7 |
| An invite or sign-in link opens the wrong app or carries a secret into a URL log | links stay `https:` to the server (the browser's landing page), opened by the app through verified app links / universal links when M7 adds them, never a custom scheme carrying a token; the preview routes (`/v1/invites/preview`, `/v1/sign-in-links/preview`) show the server and the kind before anything is redeemed | M7 |
| A stale notification tap | verify the credential and the channel before navigating; land on a safe screen with a reason (§6) | M12 |
| The microphone transmits without a press | the gate (§4) is the one owner, with the lifecycle block and the resume latch added; **the track is muted before it is published and the publication is muted again after publishing and after any republish** (`sdk.ts` lines 634–645, #501: muting after publication alone left about 5 ms unmuted per join); the OS indicator is the person's independent check; no lock-screen or notification press control; background open mic off by default and gated by demonstration | M-F7, M-L8, M-L9, M-F, M-L, M-I rows |
| A second connection as the person without the person knowing | the presence check and the words before Join or Watch (§3.2); the displaced device stops and says so (already true in the browser and the helper) | M-S rows |
| Companion or viewer identity used from a phone | never requested by the phone (§3.4); the server already ties `.screen` to a present `p<id>` and limits it to one | code review of every phone PR; an e2e assertion that the phone client never calls `…/voice/companion` |
| Guest entry points | none exist on the server (#1005) and none are built on the phone | — |
| Operator functions on a phone | an operator may sign in (password and code, ADR-012) and the idle bound applies; owner re-auth routes (`reauthAlways`) work as in the browser; nothing operator-only is added for the phone | security review of M7 |
| Approval decisions | not on the phone in this phase; D7 stands (ntfy, decisions through `conch`) | — |

Security review precedes the merge of M7 (sign-in, profiles, keystore), M11/M12 (push) and M9/M10 (production voice lifecycle), as CLAUDE.md requires for authn/authz and tokens. M4 and M5 add no authn code of their own (they use the API as the browser does) but carry a review for the credential handling in the spike.

**Out of scope in this phase, by #757 and this note** (the same list as ADR-016 Decision 10 and M1-9): phone screen broadcasting; the camera (ADR-015 is browser and desktop); global, background or hardware push-to-talk; DMs; administration beyond what every member already has; SSO; guests; store submission; approval decisions.

## 9. Where it goes in the repository, later

Only M6 creates `mobile/`. The shape proposed for it, so that M4 and M5 keep their spikes compatible with it:

```text
mobile/
  app/           React Native project: screens (M2's flows), navigation, platform adapters
  shared/        imports of web/src/schema, web/src/platform/operations.ts, the state reducers,
                 voice/gate.ts and disconnect.ts; no React DOM, no Electron, no window
  android/, ios/ the native projects: services, audio session, keystore, lifecycle
  deps-allowlist.txt, licences-allowlist.txt, .nvmrc (the web pin), README.md
spikes/mobile/android/, spikes/mobile/ios/   M4 and M5; frozen after M6 records their receipts
```

The `shared/` imports are the measured part of M6 ("avoid broad existing web/desktop refactors", #1111): `web/src/voice/connection.ts` is already transport-injected (§1.4), so M6 has only to confirm that its `import type` from `../api` compiles outside `web/` and to supply the callbacks from the phone's transport; if that confirmation fails for a reason not foreseen here, the phone gets its own thin voice client over the same `Room` interface and the gate, and the cause is filed as a browser issue, not fixed under M6.
