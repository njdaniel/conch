An ordinary Mac user downloads one app, drags it to Applications, saves their servers, chats, joins voice when they choose, holds a key or a mouse side button while another app has focus and is heard exactly while it is held, and shares a screen on configurations that were tried. Everything that makes that true on Linux (the gate, the mixer, the control protocol, the supervision rules, the Unix-socket events endpoint) is kept. What changes is the audio device layer, the key source, where the socket lives, and the fact that macOS asks the person, by name and one permission at a time, before an app may hear the microphone, watch the keyboard, see the screen or post a notification.

## 1. Target and toolchain pins

**Decision proposed.** The first macOS client supports **Macs with Apple silicon**, on:

| macOS | Apple's support status, read 2026-11-11 | Classification |
| --- | --- | --- |
| **27 Golden Gate** (27.2.1, 2026-11-09) | "The latest version of macOS is 27.2.1" ([Apple security releases](https://support.apple.com/en-us/100100)) | **supported**: the primary target; ME1 to ME15 run on it first |
| **26 Tahoe** (26.7.3, 2026-11-09) | security release the same day | **pending validation**: supported once the experiments are rerun on it |
| **15 Sequoia** (15.8.3, 2026-11-09) | security release the same day | **pending validation**, lower priority; the floor |
| 14 Sonoma (14.8.9, 2026-08-06) | no release since August; absent from the 14 September, 28 September, 26 October and 9 November rounds | **excluded** |
| 13 Ventura and older | not in the table's recent rows | **excluded** |

Apple states no servicing policy on that page (it says only which version is the latest), so the classification is read from **which versions received updates**, the current one and the two before it. That is an inference from the table and is said to be one. The floor of 15.0 is also what the design uses: the system screen picker Electron exposes is "currently available for MacOS 15+ only" (§8), and Core Audio process taps and their usage string date from 14.2 ([NSAudioCaptureUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsaudiocaptureusagedescription)). Electron 44 itself runs on "macOS (Ventura and up)" ([Electron 44.10.0 README](https://github.com/electron/electron/blob/v44.10.0/README.md)), so the floor is the design's and Apple's, not Electron's.

**Apple silicon versus Intel.** `aarch64-apple-darwin` is a Rust **Tier 1 with host tools** target ("ARM64 macOS (11.0+, Big Sur+)"); `x86_64-apple-darwin` is **Tier 2 with host tools** ("64-bit macOS (10.12+, Sierra+)") ([rustc platform support](https://doc.rust-lang.org/rustc/platform-support.html)). macOS 27 does not run on Intel Macs and macOS 26 was the last release that does (press reports of Apple's announcements: [9to5Mac](https://9to5mac.com/2026/09/09/apple-confirms-macos-27-golden-gate-launch-date-september-14/), [Six Colors](https://sixcolors.com/post/2025/06/macos-tahoe-is-the-last-release-to-support-intel/); Apple's own compatibility page was not found in this session, so this is **not verified from Apple**). Apple's developer documentation does say Rosetta "will be available through macOS 27" ([About the Rosetta translation environment](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)). An Intel build would therefore be a second architecture, on a Tier 2 Rust target, for machines that can never run the primary macOS: it is **out of the first release**. LiveKit does ship `webrtc-mac-x64-release.zip` and Electron ships Intel binaries, so nothing forbids it later. A universal binary is not proposed: it doubles the helper and the Electron framework for a platform nobody here can test.

## 2. The audio backend

**Decision proposed.** The microphone and speakers on macOS are Core Audio, through the [`cpal`](https://docs.rs/cpal/0.18.2/cpal/) crate (0.18.2, Apache-2.0, published 2026-08-16), as a third implementation of the two traits of `conch-voice-audio` (`MicSource`, `SpeakerSink`, `Pacing::Ring`): a file `audio_macos.rs` beside `audio_linux.rs`, chosen in `audio.rs` by `cfg(target_os = "macos")`, exactly the shape #892 (closed) made for the Windows sibling. `cpal` becomes a `[target.'cfg(target_os = "macos")'.dependencies]` entry. The gate, the mixer, the jitter buffers, the session loop and the control protocol are untouched: **ADR-006's platform-neutral split is kept as #892 left it.** `forbid(unsafe_code)` stays on every crate; native code is reached only through the dependency, as CLAUDE.md rule 6 says.

This does **not** reopen the Windows choice. `wasapi` was signed off for Windows on 2026-11-11 (#756); `cpal` is proposed for macOS only, and is not offered as one crate for both.

**Why `cpal`.** The helper's device rules are strict: a named device that goes away is `capture: unavailable` and is never replaced; following `default` means following the default as it changes; a switch during a transmission shuts the gate ([tui-voice.md §20.5](tui-voice.md)). They need a stable identity and to be told when a device goes. `cpal` documents both on macOS; `coreaudio-rs` documents the disconnection only, and names devices by a name that two identical headsets share. `cpal` depends on `coreaudio-rs` and `objc2-core-audio` itself, so the choice adds one line to the allowlist and the second crate arrives transitively either way.

**A note for #776, not a re-decision.** The Windows design's table says `cpal` has "no device-change or default-device-change notification". That was written from its API page. Its changelog for 0.18.0 lists `DeviceChanged` and `DeviceNotAvailable` error kinds on several hosts. The Windows choice was made and signed on other grounds too; this is recorded so that the next reader of that table does not take the sentence for current.

### 2.2 Shape of the macOS audio path

```text
Core Audio input (HAL, cpal input stream)  ─► capture ring ─► transmit gate ─► LiveKit track
remote tracks ─► jitter buffers ─► mixer ─► playback ring ─► Core Audio output (HAL, cpal output stream)
```

- **Threads.** `cpal` calls the data callback on Core Audio's own I/O thread. That callback moves samples between the buffer it is given and the lock-free rings and does nothing else, as `dmn-audio`'s callbacks do on Linux. The transmit and mix tasks look at the rings every `RING_LOOK`; nothing in the pacing changes (`Pacing::Ring`).
- **Format.** Everything inside is 48 kHz mono f32 in 10 ms frames. The helper takes the device's own configuration and converts, rather than asking Core Audio to change the hardware: a built-in microphone runs at 48 kHz (memory, not checked) but Bluetooth earphones in their two-way mode offer 16 or 24 kHz (memory, not checked), and changing a device's rate under other apps is not something a voice client should do. So a **resampler is likely needed on macOS**, the same conditional crate the Windows design names ([windows-desktop.md §2.2](windows-desktop.md)); `rubato` is already in `voice/Cargo.lock` through `dmn-audio` on Linux, at **5.0.1** (its manifest's licence is `MIT OR Apache-2.0`, read from the crate's `Cargo.toml` in the local cargo registry; `Cargo.lock` records no licence), and would become a direct, macOS-and-Windows dependency. ME3 decides, by recording what `cpal` offers and what it does to the device.
- **Device identity.** A device is named by its **Core Audio device UID**, which `cpal` carries in `DeviceId`. Apple's reference page for `kAudioDevicePropertyDeviceUID` has no text; that the UID "persists across boots" is memory, not checked. Nothing guarantees a UID fits the `set_devices` name rule (1 to 255 bytes, one line, no control character, no `"` or `\`; [tui-voice.md §20.3](tui-voice.md)), so the rule the Windows design states is adopted word for word: compatibility is **checked per device, never assumed**; a device whose UID fails it is counted in `unshown_microphones`/`unshown_speakers` and cannot be chosen; no mapping from UIDs to names is invented ([windows-desktop.md §2.2](windows-desktop.md), "Device identity"). The friendly name is the description. Real UIDs are an ME4 observation.
- **Device loss.** `DeviceNotAvailable` on the stream's error callback, for the device in use, is the device going away (the changelog states it for default output streams; a named input device is ME4): the gate shuts with no tail, the state shows `capture: unavailable` and `no_microphone`, nothing is substituted. `DeviceChanged` matters only when the side follows `default`; then the stream moves, and a transmission under way ends first, as a `set_devices` to a new microphone does. The callback posts to the session loop and returns. Mac-specific cases for ME4: closing the lid with an external display removes the built-in microphone; connecting Bluetooth earphones changes both defaults at once; opening their microphone drops their playback to the two-way codec (memory, not checked), which the person hears as worse sound the moment they join.
- **Microphone permission.** §9. A denied microphone is **not a failed join**: as on Linux and Windows, "a missing microphone is not [`audio_unavailable`]: it is `capture: unavailable` and the session goes on" ([tui-voice.md §6](tui-voice.md); [windows-desktop.md §2.2](windows-desktop.md), "Microphone privacy"), so the person joins and listens, with `capture: unavailable` and `no_microphone` among `blocked`. **The macOS hazard** is that the system may not refuse the device at all: a denied app may be handed a stream of silent samples instead of an error (memory, not checked; ME5). A helper that trusted such a stream would show `capture: on` and transmit silence on every press. So the backend never infers the permission from what the stream delivers: **main, which can read the status, tells the helper** (§9), and the helper opens no microphone when it is told there is none.

### 2.3 Echo cancellation

MacBooks are used on their built-in speakers and microphone far more than a gaming PC is, so #186 (echo) weighs more here than on the other two platforms. Core Audio has an answer: the voice-processing I/O unit, `kAudioUnitSubType_VoiceProcessingIO`, "an audio unit that interfaces to the audio inputs and outputs ... and provides voice processing features", with "bus 0 provides output to hardware and bus 1 accepts input from hardware" ([Apple](https://developer.apple.com/documentation/audiotoolbox/kaudiounitsubtype_voiceprocessingio)); `coreaudio-rs` exposes it as `IOType::VoiceProcessingIO`. It is one unit for both directions, because the canceller needs the played signal as its reference, so adopting it replaces the two `cpal` streams with one unit on that path and is a second backend shape, not a flag.

**Proposed:** the first macOS backend is the plain path of §2.2 and says what Linux and Windows say: wear headphones. Voice processing is **MF12**, a measured follow-up like the Windows F10 (#899): build it behind the same traits, measure the echo a second listener hears with built-in speakers, and record the side effects (it lowers other apps' volume while active, and it changes the microphone's processing; both memory, not checked) before offering it. It is not promised.

### 2.4 Standalone commands and configuration

`conch-voice join`, `devices`, `config` run on macOS with the same semantics once the port below is done. `conch-voice keys <device>` reads an evdev device and does not exist on macOS (§4.5).

**The configuration layer does not carry over unchanged** (corrected in review, 2026-11-11; the first draft said it did). Most of it does: macOS is a Unix, so the mode-bit check of `voice.toml` and `credentials.json`, the `(dev, ino)` identity check and the write-temporary-then-rename replacement are meaningful as written, and none of the Windows work of [windows-desktop.md §2.7](windows-desktop.md) (#904) is needed. Two things are wrong on macOS as the code stands, and they are a port of their own, **MF19**, in the way F15 is for Windows:

1. **Discovery: the Go client and the Rust helper would look in different directories.** `internal/cli/credentials.go` takes the default from Go's `os.UserConfigDir` (`configDir`), and "on Darwin, it returns `$HOME/Library/Application Support`" ([Go `os/file.go`](https://raw.githubusercontent.com/golang/go/master/src/os/file.go)); `XDG_CONFIG_HOME` is not read there. The Rust `default_config_dir` (`voice/crates/conch-voice-api/src/login.rs`) hard-codes the Linux rule, `$XDG_CONFIG_HOME/conch`, else `$HOME/.config/conch`. So `conch login` on a Mac would write `~/Library/Application Support/conch/credentials.json` and a standalone `conch-voice join` would look in `~/.config/conch` and find no login. The shared vectors do not catch it: `internal/cli/testdata/config-dir-vectors.json` holds Linux paths and `TestConfigDirSharedVectors` skips itself off Linux. **Proposed:** the Rust side follows the Go side, since `conch` is the program that writes the login and a Mac user may already have one: under `cfg(target_os = "macos")`, `CONCH_CONFIG_DIR` first as today, else `$HOME/Library/Application Support/conch`, with `XDG_CONFIG_HOME` ignored as Go ignores it. A set of **Darwin vectors** is added beside the Linux ones and run by both: the Go test on a macOS runner, the Rust test under the same `cfg`. The desktop app is unaffected either way, because main passes `CONCH_CONFIG_DIR` per profile. Changing the Go default to the XDG rule on macOS instead was weighed and is not proposed: it would move an existing Mac user's login.
2. **`O_NONBLOCK` has Linux's value.** `voice/conch-voice/src/config_cmd.rs` defines `const O_NONBLOCK: i32 = 0o4000` by hand ("`O_NONBLOCK` on Linux ... std has no name for it and `libc` is not a dependency here") and passes it when it opens `voice.toml`, so that a FIFO planted at the path cannot block the command. On Darwin `O_NONBLOCK` is `0x00000004` and `0x00000800` is `O_EXCL` ([xnu `bsd/sys/fcntl.h`](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/fcntl.h)). Compiled for macOS as it stands, the open would not be non-blocking, and a FIFO swapped in between the inspection and the open would hang `conch-voice config set`; what `O_EXCL` does on an open without `O_CREAT` is not something to rely on either. **Proposed:** the constant is per target (`0o4000` on Linux, `0o4` on macOS), and the existing FIFO test runs on macOS, where it is the test that would have caught this.

Until MF19 lands, a macOS helper is correct only when its owner sets `CONCH_CONFIG_DIR`, which the desktop app always does; the standalone commands are not offered on macOS before it.

What else does **not** carry over is in the helper's own code, and is MF2: `devices::current_uid()` reads the owner of `/proc/self`; `keydev.rs` and the udev text in `devices.rs` are Linux's; `managed::open_event_pipe` reopens `/proc/self/fd/3` (§3.2).

### 2.5 What stays platform-neutral

As [windows-desktop.md §2.5](windows-desktop.md): `conch-voice-audio`, `conch-voice-control`, `conch-voice-api`, `session.rs`, `transmit.rs`, `receive.rs`, and `managed.rs` apart from the plumbing of §3. The `MicSource`/`SpeakerSink` traits are the platform boundary and gain nothing Mac-specific.

### 2.6 `conch.voice_devices.v2` should name `coreaudio`

The Windows design proposed `conch.voice_devices.v2`, replacing v1's `pipewire: ok | unavailable` with `backend` (`pipewire` or `wasapi`) and `audio` ([windows-desktop.md §2.6](windows-desktop.md)); it is #891 and is **not yet published**. A macOS helper writing either of those two values would be lying. **Requested of #891:** the closed set of `backend` values includes `coreaudio` from the first published v2, with one macOS golden fixture carrying device UIDs as names. Adding a value to a published closed enum later would be a breaking change and a v3; adding it before publication costs a line. This is a comment on a schema that already needs the owner's sign-off, not a new shape.

**Open questions.** ME3 (formats, period, glitch-free 10 ms, whether `cpal` touches the device's rate, the resampler), ME4 (identity, loss, default follow, lid, Bluetooth), ME15 (voice processing). **Follow-up:** MF3, MF4, MF12.

## 3. The managed transport on macOS

**Decision proposed.** The Electron owner starts `conch-voice managed --events-pipe <absolute path>` with standard input as the command channel and an owner-created Unix socket as the events channel, **exactly as on Linux** ([linux-desktop.md §5](linux-desktop.md); the helper's half is #937, merged, in `voice/conch-voice/src/channel.rs`). The shared contract is not restated here: one command channel, one events channel, **authority only on the command channel from the spawning process**, owner loss by EOF on either or by any byte received on the events channel, the attach line `conch.voice_control_pipe.v1` as a spawn-to-pipe binding and **not authentication**, the six owner rules, same-user code out of scope ([windows-desktop.md §3.4](windows-desktop.md); [linux-desktop.md §5.2](linux-desktop.md)). No message, bound or fixture changes.

### 3.1 What carries over, and why it can

- **The socketpair finding.** libuv creates `'pipe'` stdio entries with `socketpair` in its Unix process code, which macOS shares with Linux ([libuv `src/unix/process.c`](https://raw.githubusercontent.com/libuv/libuv/v1.x/src/unix/process.c)), so an Electron owner on macOS cannot hand over a FIFO on fd 3 either, and the events socket is the route for the same reason ([linux-desktop.md §5.1](linux-desktop.md)).
- **The socket.** `net.createServer().listen(path)` in main and `std::os::unix::net::UnixStream::connect(path)` in the helper are the same safe calls. `symlink_metadata`, `FileTypeExt::is_socket`, `MetadataExt::uid` and `mode` are `std::os::unix` and exist on macOS.
- **Signals and stop.** `SIGTERM` and `SIGINT` through tokio's Unix signals; the owner's stop is `leave`, close standard input and the events server, `child.kill('SIGTERM')` at `StopTermAfterMS`, `child.kill('SIGKILL')` at `StopKillAfterMS`, wait for `exit` ([linux-desktop.md §5.3](linux-desktop.md), the Electron column). Spawn **without** `detached`. Never `pkill`, `killall` or a process name.
- **The parent watch.** `std::os::unix::process::parent_id` is `getppid` and works on macOS; a child whose parent dies is given to `launchd` (memory, not checked), so the value changes and `watch_parent` fires as it does on Linux.

### 3.3 The events socket's directory

Main takes Electron's `app.getPath('temp')` (or `$TMPDIR`), and **verifies it as the Linux owner verifies `$XDG_RUNTIME_DIR`** ([linux-desktop.md §5.2](linux-desktop.md)): `lstat`, a directory and not a symlink, owned by main's own uid, `mode & 0o077 == 0`. A failed check, or an unset variable that falls back to the shared `/tmp`, is a refusal with a reason (the existing `runtime-dir-not-owned` and `runtime-dir-not-private`), **never a fallback**. It then makes one directory, `conch`, with mode 0o700, checks that too, and binds a random name there, with the bind-then-retry and never-`readableAll` rules unchanged. **The profile id is not part of the path on macOS** (below), and so the stale sweep changes: the directory is shared by every profile and every running instance of the app, so main unlinks **only the sockets it created itself**, when the helper has attached, when the attach fails, and on stop. It does not sweep the directory, because an entry it did not create may be another instance's live endpoint. A socket left by a crash is an empty inode under a 72-bit random name that is never reused, in a directory the system clears (memory, not checked). The helper's own checks (an absolute path, a socket owned by its uid, a parent directory it owns with mode exactly 0o700, never an abstract name) need no change beyond §3.4; macOS has no abstract socket namespace, so that refusal is simply never reached.

**The path budget, counted** (corrected in review, 2026-11-11; the first draft did not count it and kept the profile id in the path). `sun_path` is 104 bytes on macOS against Linux's 108, **four fewer**, so the longest path is 103 bytes against 107. The pieces:

| Piece | Bytes | Source |
| --- | --- | --- |
| the per-user temporary directory, without a trailing slash | about 48 | memory, not checked: `/var/folders/`, two characters, `/`, thirty characters, `/T`. ME2 records the real one |
| `/conch` | 6 | this design |
| `/` and the socket's name, `e-` plus 12 base64url characters plus `.sock` | 1 + 19 | `randomName` in `desktop/main/voice/endpoint.ts` (`randomBytes(9).toString('base64url')`) |
| **total without a profile id** | **about 74** | 29 bytes to spare |
| `/` and a profile id | 2 to 65 | `validProfileId` in `desktop/main/vault/files.ts` accepts 1 to 64 bytes |
| total with a profile id, as on Linux | about 76 to 139 | **over 103 for any id longer than 28 bytes** |

So the Linux layout, `conch/<profile-id>/<name>`, does not fit on macOS for ids the app accepts, and the owner would refuse voice with `socket-path-too-long` for them. **Proposed: on macOS the socket's parent is `<temporary directory>/conch`, with no profile id in it.** Nothing is lost by that: the directory keeps other users out whichever profile it serves, each start binds its own random name, and a same-user process is out of scope with or without a per-profile directory. Bounding the profile id instead (a shortened or hashed form) was weighed and is not proposed: it is a new mapping rule for no gain. The owner still computes the full path's length before listening and fails closed with the reason if it does not fit; ME2 records the real length. If the real temporary directory turns out much longer than memory says, the fallback to weigh is a directory main creates under its own `userData` with mode 0o700, which is longer still for a long account name and is not cleared at restart, so it is second choice. The directory is checked every time; one the system has cleaned away between two sessions is recreated, not assumed.

### 3.4 The helper's own uid without `/proc`

`channel::check_endpoint` compares the socket's and its directory's owner with the helper's uid. Three ways to learn it under `forbid(unsafe_code)`:

1. **`rustix::process::getuid()`**, a safe function (memory, not checked) of a crate already in `Cargo.lock` at 1.1.5 through `tempfile` and the PipeWire bindings. As a direct dependency it is a line in `voice/deps-allowlist.txt` and Nick's sign-off. It also serves Linux, and would retire the `/proc/self` read there.
2. **No new dependency:** the helper creates a file of its own with `create_new` in the socket's directory, reads that file's owner, and removes it. A new file is owned by the process's effective uid. It writes to disk to learn a number, and it needs write access to a directory the helper otherwise only reads.
3. `libc::getuid`: `unsafe`. Refused.

**Proposed: route 1**, with route 2 if the sign-off is withheld. Either way `devices::current_uid` gets one implementation per `cfg`, and the tests that stand in for another user keep working.

**Platform-neutral.** Every message, bound, phase and fixture; the attach line; the owner's rules; `managed.rs`. **Open questions.** ME2 (the real temporary directory, its mode and length; the socket from a second user account; the attach and a minute of events; the allowlist), ME6 (owner death, Force Quit, App Nap, measured bounds). **Follow-up:** MF2, MF7.

## 4. Global push-to-talk

**Decision proposed.** The helper creates one **listen-only** Quartz event tap, `CGEventTapOptions::ListenOnly` ("specifies that a new event tap is a passive listener", [Apple](https://developer.apple.com/documentation/coregraphics/cgeventtapoptions/listenonly)), for key down, key up, other-mouse-button down and other-mouse-button up, on a thread of its own with a Core Foundation run loop, and turns those into presses and releases for the bindings: a key down for the bound key code that is not an auto-repeat is a press, the key up is a release; an other-mouse-down whose button number is the bound one is a press, the matching up a release. These feed the existing push-to-talk machine in `conch-voice-control` through the same `Input::Key` the evdev reader uses. Nothing downstream knows the operating system.

### 4.1 What the documentation establishes

- An event tap is created with `CGEvent.tapCreate(tap:place:options:eventsOfInterest:callback:userInfo:)` and "after creating an event tap, you can add it to a run loop" ([Apple](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsofinterest:callback:userinfo:))). The call returns nothing when the tap cannot be created.
- That page's own condition is from another era: taps "receive key up and key down events if ... the current process is running as the root user" or "access for assistive devices is enabled". Since macOS 10.15 there are `CGPreflightListenEventAccess()` and `CGRequestListenEventAccess()` ([Apple](https://developer.apple.com/documentation/coregraphics/cgpreflightlisteneventaccess()); the pages have no text), and System Settings has **Input Monitoring**: "Some apps can monitor your keyboard, mouse, or trackpad even when you're using other apps" ([Mac User Guide](https://support.apple.com/guide/mac-help/control-access-to-input-monitoring-on-mac-mchl4cedafb6/mac)). That a listen-only tap needs Input Monitoring and **not** Accessibility is the common account and is memory, not checked: **no Apple page read here says it in so many words.** It is ME7's first finding.
- The tap tells its owner when the system switches it off: `tapDisabledByTimeout` ("the event tap is disabled because of timeout") and `tapDisabledByUserInput` arrive as event types ([Apple](https://developer.apple.com/documentation/coregraphics/cgeventtype/tapdisabledbytimeout)). This is the opposite of the Windows hook that is "silently removed", and it is what makes a tap acceptable where a hook was not.
- Mouse buttons: "Quartz supports up to 32 mouse buttons. The first three buttons are specified using these three constants. Additional buttons are specified in USB order using the integers 3 to 31" ([CGMouseButton](https://developer.apple.com/documentation/coregraphics/cgmousebutton)). So the first side button is expected to be number 3 and the second 4; a vendor's driver can remap them, and ME7 records the numbers real mice send.
- **Secure Input.** While any process has secure event input enabled, the system will "stop passing keyboard events to any intercept process ... whether that process is in the foreground or background", and an event tap is one of the three intercept techniques named ([TN2150, "Using Secure Event Input Fairly"](https://developer.apple.com/library/archive/technotes/tn2150/_index.html), 2007, archived). Password fields enable it; "a process which enables secure event input and leaves secure event input enabled for the duration of the program, can affect all keyboard intercept processes, even when the secure event process has been moved to the background". The note speaks of keyboard events only.

### 4.3 The dependency

[`core-graphics`](https://docs.rs/core-graphics/0.25.0/core_graphics/event/struct.CGEventTap.html) 0.25.0 (MIT OR Apache-2.0, published 2025-05-27, the Servo project's bindings) has what is needed as safe functions: `CGEventTap::new(tap, place, options, events_of_interest, callback)` taking a `Fn(CGEventTapProxy, CGEventType, &CGEvent) -> CallbackResult + Send + 'static`, `enable()`, `CGEventTapOptions::ListenOnly`, the event types `KeyDown`, `KeyUp`, `FlagsChanged`, `OtherMouseDown`, `OtherMouseUp`, `TapDisabledByTimeout` and `TapDisabledByUserInput`, and the integer fields `KEYBOARD_EVENT_KEYCODE`, `KEYBOARD_EVENT_AUTOREPEAT` and `MOUSE_EVENT_BUTTON_NUMBER` ([`event.rs`](https://raw.githubusercontent.com/servo/core-foundation-rs/main/core-graphics/src/event.rs), read on the main branch; the constructors were confirmed on the 0.25.0 documentation page). Its `new_unchecked` is `unsafe` and is not used. The run loop is `core-foundation`'s `CFRunLoop` (0.10.1, MIT OR Apache-2.0), **already in `Cargo.lock`** through `security-framework`; using it directly makes it a second allowlist line with no new crate in the lock.

Not in that crate: the listen-access preflight and request functions (not found in `event.rs`), and a key-state query (`event_source.rs` wraps only the constructor). So, as on Windows, **the helper cannot ask whether a key is down** from safe code, and learns that the permission is missing from the tap failing to be created.

Each crate is a new direct dependency and **needs Nick's sign-off**. The audit before it is allowed is the Windows one in its macOS form ([windows-desktop.md §4.3](windows-desktop.md)): the options are exactly `ListenOnly`; the events of interest are exactly the four transitions (plus `FlagsChanged` only if modifier bindings are accepted, §4.5); no code path posts an event or returns anything but "keep"; the crate's features are the minimum; and the "no key code in any output" test of the key path is rerun on macOS against the helper's standard error and events. MF5.

### 4.4 Fail-closed rules on macOS

The shared rules are [linux-desktop.md §7.1](linux-desktop.md) and [windows-desktop.md §4.4](windows-desktop.md), adopted whole: repeats never hold or reopen; an unknown initial state is not a press; loss shuts the gate with no tail; a stalled input thread shuts the gate; focus changes do nothing; nothing but bound transitions leaves the input module; the missed-release bound in a desktop session is **30 s** (Nick, 2026-10-28). The macOS forms:

- **Repeats.** A key down whose auto-repeat field is set is nothing. A key down for a key the machine already holds is nothing either, whatever the field says.
- **An unknown initial state is not a press.** A binding is armed only by an observed release, because the helper cannot ask whether the key is down (§4.3). A key held when the helper starts transmits nothing until it is released once.
- **A disabled tap is the key source lost.** On `TapDisabledByTimeout` or `TapDisabledByUserInput` the gate shuts with no tail, the state shows `ptt: lost` with `ptt_problem: read_failed`, the tap is re-enabled, and every binding returns to unarmed, so a fresh release and press are needed. A tap that cannot be re-enabled stays `lost`.
- **A refused tap is a named state.** If the tap cannot be created when the helper starts (the permission is not granted), the state shows **`ptt: unavailable` with `ptt_problem: refused`**: `unavailable` is "a key device is configured and has not been read since the helper started; `ptt_problem` says why", and `refused` is in the problem vocabulary ([pkg/schema/voice_control.go](../../pkg/schema/voice_control.go)). `lost` is for a tap that was working and stopped (above). Voice still joins, the gate cannot be opened by a key, and §9 says what the person is told.
- **A stalled input thread shuts the gate**, by the watchdog tick the Windows design describes: no tick from the run-loop thread for one `VoiceControlOwnerPollMS` while a key is held is `ptt: lost`.
- **Secure Input.** Two effects, both fail-closed for the microphone and neither detectable from safe code (`IsSecureEventInputEnabled` is a Carbon call). A **press** made while Secure Input is on is not seen: the talk key does nothing, and the help text says why ("a password field, or an app with secure keyboard entry turned on, is holding the keyboard"). A **release** that happens after Secure Input turned on mid-hold is not seen: the transmission runs to `max_transmit_secs`, 30 s, with `transmitting: true` showing the whole time. A **mouse-button** binding is expected to be unaffected, since the note speaks of keyboard events; that is ME8, and if it holds, the mouse binding is the recommendation for anyone who hits this.
- **Lock, sleep and switching users.** The owner sends `set_mute true` on `lock-screen` and on `user-did-resign-active`, and `leave` on `suspend` (§10). Whether a key up that happens on the lock screen reaches the tap is ME8; the three bounds (30 s, the owner's mute, the visible state) are the answer if it does not.
- **Device removal.** A `CGEventTap` reports events, not devices: unlike evdev and Raw Input there is no removal notice. Whether unplugging a keyboard with the key held produces a key up is ME7. If it does not, the bound is `max_transmit_secs`, and this is the one place macOS is weaker than the other two; it is stated in the matrix, not hidden.
- **Full-screen apps and games.** A session-level tap sits between the window server and applications, so a full-screen Space is not expected to matter; nothing read here says so, and it is ME7 per app. Anti-cheat on macOS is rarer than on Windows; the same rule applies (per title, recorded, never worked around).
- **Injected input** opens the gate as real input does, as on Windows: a same-user process that can post events can already read the token.

### 4.5 Configuration

`voice.toml` `[keys]` on macOS names bindings by **virtual key code** and by mouse button: `talk = "kc:50"`, `talk = "mouse:4"` (the fourth button, number 3 on the wire of §4.1). Virtual key codes name positions on the keyboard, not letters (memory, not checked), which is the property the Linux `KEY_*` codes and the Windows scan codes were chosen for. The grammar joins the one #896 defines for Windows; it is configuration, not a wire shape. **Modifier-only bindings** (Right Option as the talk key) arrive as `FlagsChanged`, which carries the new modifier state rather than a down or an up for one key; they are accepted only if ME7 shows a press and a release can be told apart for left and right keys, and are otherwise refused by `config set` with a reason. **Binding capture for the UI** happens in the focused Electron window, as on Windows and Linux: the renderer reads `KeyboardEvent.code` and `MouseEvent.button`, and main translates to the `[keys]` form by a fixed table and writes it with `config set`. Capturing a binding needs no permission; **using** it in the background does.

**When the permission is actually asked for.** Saving a binding is `conch-voice config set`, which edits `voice.toml` and exits: it creates no event tap, so **saving asks for nothing**. The request is made by the first tap the helper creates, which is at the **next Join with a talk key bound** (memory, not checked, that creating the tap raises the system's prompt; ME5, ME7). So the order the person sees is: they save a key and the settings screen says, in the app's own words, that macOS will ask to let Conch monitor input the next time they join voice, and why; at that Join the system asks; if they refuse, the session shows `ptt: unavailable` with `ptt_problem: refused` and the sentence of §9. A request made at save time, by a one-shot helper command that only creates a tap and reports, was weighed: it would put the system's prompt next to the act that caused it, which is better, but it is a new helper command and it is not known that the grant made for a one-shot process carries to the session's helper. It is left to MF9 with ME5's finding, not proposed now.

**Rebinding during a session restarts the helper** (`leave`, then `join`) in the first version, exactly as on Windows ([windows-desktop.md §4.5](windows-desktop.md)): the helper reads `voice.toml` once, when it starts, and a `set_keys` command would be a `conch.voice_control.v3` matter that is not proposed. The app says that changing the key will leave and rejoin voice, and does it only on the person's confirmation.

**Platform-neutral.** The machine, the `KeyEvent`/`DeviceState` vocabulary, `ptt`/`ptt_problem`, the release tail, `max_transmit_secs`. **Open questions.** ME7, ME8. **Follow-up:** MF5, MF6.

## 5. Privilege and security boundaries

**Decision proposed.** The app and the helper run as the signed-in user. No root, no `sudo`, no privileged helper tool, no kernel extension, no system extension, no DriverKit driver, no login item installed silently. **Nothing in the product, its documentation or its support answers tells anyone to disable System Integrity Protection, Gatekeeper, the hardened runtime, or a Privacy & Security setting**, to strip a quarantine attribute, or to grant Full Disk Access. Where macOS does not deliver something to an ordinary app, the client says so.

- **Privacy permissions (TCC)** are the person's decision, asked for one at a time (§9). A denied permission is a state with a name and a sentence. The app never retries a prompt in a loop and never scripts System Settings.
- **Accessibility is never requested.** A listen-only tap is specified so that it is not needed. If ME7 shows that a listen-only tap needs Accessibility on a supported macOS after all, the design **stops and comes back to Nick**: a permission that allows an app to control the computer is a different thing to ask of a chat client's users than one that lets it see a key.
- **Secure Input** is honoured by going deaf (§4.4), never bypassed.
- **Keylogging surface.** A listen-only tap is handed every key and mouse-button event in the session. The Linux and Windows discipline holds: only bound transitions leave the input module; no key code, count or time is kept, logged or sent. The README says what the permission means before saying how to grant it, as it does for the udev rule.
- **The hardened runtime** is on for every executable in the bundle, with the entitlements of §12.3 and no others.
- **No listener, no secret in argv:** §3.
- **The renderer:** context isolation, sandbox, no Node integration, validated IPC, the Electron fuses already in `desktop/build/electron-builder.config.json`: #770's rules, unchanged.

**Open questions.** ME7, ME8. **Follow-up:** none of its own.

## 6. Where input lives

**Shared, not re-decided:** input lives in the helper; no command of `conch.voice_control.v1` or `v2` presses or releases; **no control command opens the gate**; bindings are configuration ([windows-desktop.md §6](windows-desktop.md); [linux-desktop.md §7.2](linux-desktop.md)).

**Where macOS differs.** Only in one risk. Input Monitoring is granted to an identity the system chooses (§3.2, last rows). If ME5 shows that a tap created by the bundled helper is refused however the permission is set, because the grant attaches to the app and is not extended to its child, the alternative is not "main owns the tap": Electron has no press-and-release API, and a native Node module in main is a larger departure than this design may make. The alternative would be the versioned trusted-input channel the Linux design names for the portal case (`conch.voice_input.v1`), with a small signed input agent as its source. **That is a hypothesis to rule out at ME5, not a proposal**, and nothing is designed for it here.

## 7. Native voice plus screen capture

**Shared, not re-decided: model B**, accepted by Nick on 2026-10-28 for both desktops ([windows-desktop.md §7](windows-desktop.md); [linux-desktop.md §6](linux-desktop.md), which is the later word). The Rust helper is the person's one voice participant; Electron is a conchd-issued companion under a derived identity for screen video; one playback owner per audio source (#906, merged); the companion's grant is `["screen_share"]` only, with audio added by a permission update on main's request (#898, merged) and one companion per person (#897).

**Where macOS differs.** Nothing in the model. The check the Linux design made for itself is repeated here: no macOS fact found in this research forces model A or forbids B. Chromium's capture on macOS is its own (ScreenCaptureKit; memory, not checked) and independent of the helper; the companion stays off voice by grant or by `autoSubscribe: false` plus #906; the Keychain, Core Audio and `powerMonitor` are the same interfaces A would rely on. The macOS-only consequence is in audio (§8): the helper is a **separate process** from the one that captures, so "exclude my own audio" switches that work per process do not cover the call.

**Open questions.** ME11: the Windows E10 list, run once with a macOS helper and the Electron companion (both connections stay up; voice plays once; the helper never plays its own companion). **Follow-up:** none new; #897, #906.

## 8. Screen and window share, and audio

### 8.1 The picture

**Decision proposed.** The share uses **the operating system's picker and nothing else**: Electron's `session.setDisplayMediaRequestHandler(handler, { useSystemPicker: true })`. "`useSystemPicker` allows an application to use the system picker instead of providing a specific video source from `getSources`. This option is experimental, and currently available for MacOS 15+ only. If the system picker is available and `useSystemPicker` is set to `true`, the handler will not be invoked" ([Electron 44.10.0 `session`](https://github.com/electron/electron/blob/v44.10.0/docs/api/session.md)). Underneath is ScreenCaptureKit's `SCContentSharingPicker`, "a picker presented by the operating system for managing frame-capture streams", macOS 14.0 and later ([Apple](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker)). Every supported macOS (15, 26, 27) has it, which is one reason the floor is 15.

This is the Linux decision in its macOS form. On Linux the screen-cast portal's picker is the only chooser and "a chooser that main builds from `desktopCapturer` names and thumbnails" is not offered ([linux-desktop.md §8](linux-desktop.md), Q-D4-4). The reasons hold here: the system's picker shows the person exactly what will be shared, in the system's own interface; main never enumerates every window's title and thumbnail; and a picked source is consent for that source alone.

**The permission.** Capturing the screen "requires user consent on macOS 10.15 Catalina or higher, which can detected by `systemPreferences.getMediaAccessStatus`" ([Electron 44.10.0 `desktopCapturer`](https://github.com/electron/electron/blob/v44.10.0/docs/api/desktop-capturer.md)); the setting is "Screen & System Audio Recording", where "you can allow apps to record both your screen and audio, or just your audio" ([Mac User Guide](https://support.apple.com/guide/mac-help/control-access-screen-system-audio-recording-mchld6aa7d23/mac)). Whether a share made through the system picker needs that permission at all, or is consent by itself, is **not stated on the pages read** (that the picker avoids the prompt, and that recent macOS re-asks periodically for apps that capture without it, are memory, not checked). ME9 records both.

**If the experimental option does not work** in the pinned Electron (ME9), the alternative is `desktopCapturer.getSources` with a chooser main builds, which needs the Screen Recording permission and shows main every window title. That is a real decision, not a silent fallback: it comes back to the principal with ME9's receipt.

Quality, the rotation rule and the stop rules are the shared ones: 720p30 by default and 1080p30, nothing unmeasured; the share ends on a room renewal and says so; a stop names its claim ([linux-desktop.md §8, §9](linux-desktop.md)). Source closed, minimised, a full-screen Space, a second display unplugged and protected content are capture-side facts for ME9, with "unsupported" as an allowed answer.

### 8.2 The sound

**Shared, not re-decided:** the three scopes (none; this application; everything but the call), **off by default**, with its own consent and its own mute, and a bare loopback of the whole output never offered as "system audio" ([windows-desktop.md §8](windows-desktop.md)); the refusal of application audio for the call's own process tree (#905).

**Decision proposed for macOS: a share is silent, and the app says so at the moment of sharing**, as on Linux (#1552), until a route that leaves the call out is demonstrated. Main never asks conchd for the companion's audio permission on macOS until then, so the companion's grant never carries `screen_share_audio`.

| Scope | macOS route | Rebroadcasts the call? | Status |
| --- | --- | --- | --- |
| none | — | no | default, and the only scope in the first release |
| whole output through Chromium | `audio: 'loopback'` in the display-media handler. **Electron's own documentation disagrees with itself at 44.10.0:** `session.md` says loopback "is currently only supported on Windows"; `desktop-capturer.md` says that "as of Electron `v39.0.0-beta.4`, Chromium made Apple's new `CoreAudio Tap API` the default for desktop audio capture" on macOS 14.2 and later, that it needs `NSAudioCaptureUsageDescription`, and that a missing key "will still create a dead audio stream however no warnings or errors are displayed" | **yes**: it captures the output device, and the helper plays the room on that device | **not offered** as "system audio", on any reading. Under model B the capturing process is Chromium and the process that plays the call is the helper. Whether the system counts a bundled helper as "your app" for this switch, or for an `excludingApplications` filter, is not documented and is ME10. Until it is measured, nothing is built on it.

**What a native route would need,** and so what MF11 has to decide: a safe crate (`cpal`'s loopback is a tap of an output device, and whether it takes an exclusion list was **not checked**; [`screencapturekit`](https://crates.io/crates/screencapturekit) 11.1.2, MIT OR Apache-2.0, exists and was **not evaluated**; `objc2-core-audio` is `unsafe`), the `NSAudioCaptureUsageDescription` string, and the same plumbing question the Windows design left to W4: a share's sound captured by the helper has to reach the share the companion publishes. That is #778's design to make or refuse, for both platforms at once.

**Platform-neutral.** The scopes, off by default, the feedback test before any route is offered (remote speech alone, against a measurement listener). **Open questions.** ME9, ME10. **Follow-up:** MF10, MF11.

## 9. Permissions: what is asked, when, and what denial looks like

macOS asks the person before each of these, remembers the answer per app, and does not ask twice: "if access has already been requested and denied, it must be changed through the preference pane; an alert will not pop up" ([Electron 44.10.0 `systemPreferences`](https://github.com/electron/electron/blob/v44.10.0/docs/api/system-preferences.md)). So the first ask is the only one the app gets, and it is spent **at the moment the person does the thing that needs it**, after a sentence of the app's own saying why.

**Rules for all of them.** Nothing is requested at launch. Main reads the status before it acts; the renderer is told a state, never given a way to prompt. A denied permission is a named state with one sentence and a button that opens the right pane of System Settings; there is no retry loop. After a change in System Settings, the app says plainly if it must be reopened. The usage strings live in the app's `Info.plist`; without the key and the entitlement "the system terminates your app" ([Apple](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)).

| Permission | Who needs it | Asked when | How | Denied | Reset or revoked while running |

## 11. Credentials

**Shared, not re-decided:** the shell keeps each profile's token with Electron's `safeStorage`, asynchronous API; if encryption is unavailable the profile offers session-only login and says why; nothing plaintext-equivalent is persisted; the token reaches the helper as `CONCH_TOKEN` with `credential: env` in an environment built from empty; it is never in argv, logs or the renderer ([windows-desktop.md §9.1](windows-desktop.md); [linux-desktop.md §4.1](linux-desktop.md)). `desktop/main/vault/classify.ts` already classifies `darwin` as one provider, `protected`.

**Where macOS differs.**

- **What the protection is.** "Encryption keys are stored for your app in Keychain Access in a way that prevents other applications from loading them without user override. Therefore, content is protected from other users and other apps running in the same userspace" ([Electron 44.10.0 `safeStorage`](https://github.com/electron/electron/blob/v44.10.0/docs/api/safe-storage.md)). That is **stronger than the Windows wording** (DPAPI protects from other users only), so the sentence shown to the person on macOS is the macOS one, not the Windows one that `classify.ts`'s comment quotes. "Without user override" is the limit: the person can allow another app at the Keychain's prompt.
- **It depends on the signature.** "On macOS, your app should be code signed for `safeStorage` to behave consistently. Without a valid, consistent signature, macOS may not recognize different builds of your app as the same application, which can cause the Keychain to re-prompt the user for permission on every update" (same page). So the saved-login experience of an unsigned preview is not the product's.
- **The call can stop and ask.** "Access to the system Keychain is required and these calls can block the current thread to collect user input." The asynchronous API is used, as the shared design says, and a Keychain prompt that is **denied** is treated as encryption unavailable: session-only login, with the reason. Whether Electron reports a denial as an error or as unavailability is ME13, and the vault's classification is checked against it.
- **The cookie-encryption fuse.** The existing configuration turns on `enableCookieEncryption`; Electron says it "uses the same OS-level access to the Keychain as `safeStorage`, so it has the same code signing requirement" ([code signing](https://github.com/electron/electron/blob/v44.10.0/docs/tutorial/code-signing.md)). So an unsigned build may meet a Keychain prompt at launch, before any login is saved (ME13).
- **`credential: stored`** would work in a macOS helper, since the mode check is Unix; the Electron owner still uses `env` only.

**Open questions.** ME13. **Follow-up:** MF16.

### 12.2 Signing, notarization and stapling: the account and its cost (Nick's decision; recorded, not made)

What Apple requires: "Beginning in macOS 10.15, all software built after June 1, 2019, and distributed with Developer ID must be notarized"; the notary service "is an automated system that scans your software for malicious content, checks for code-signing issues"; it "generates a ticket for you to staple to your software"; and "to upload a macOS app to be notarized, you must enable the Hardened Runtime capability" ([Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution); [Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)). Notarization "is not App Review". Submission is by `notarytool` (the older `altool` is no longer accepted). electron-builder runs it when one of three sets of credentials is in the environment, and recommends the first: an App Store Connect API key (`APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`), an Apple Account with an app-specific password, or a keychain profile (`macOptions.ts`, `notarize`).

### 12.3 Hardened-runtime entitlements, each one justified

"Make sure to use only the entitlements that are absolutely necessary for your app's functionality"; "you add entitlements only to executables. Shared libraries, frameworks, and in-process plug-ins inherit the entitlements of their host executable" ([Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)). A spawned executable is not an in-process plug-in: `conch-voice` gets its own, and does not inherit the app's.

| Executable | Entitlement | Why | Status |
| --- | --- | --- | --- |
| Conch (main) and Electron's own helper apps (`Conch Helper`, and its Renderer, GPU and Plugin forms) | `com.apple.security.cs.allow-jit` | V8 compiles JavaScript at run time; the entitlement is what lets a hardened process "create writable and executable memory using the `MAP_JIT` flag" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit)), and electron-builder warns that "your app may crash if the right entitlements are not set like `com.apple.security.cs.allow-jit` for example on arm64 builds with Electron 20+" | **included** |
| `conch-voice` | `com.apple.security.device.audio-input`, **and nothing else: no `allow-jit`** | it is the process that opens the microphone: "whether the app may record audio using the built-in microphone and access audio input using Core Audio" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.audio-input)) | **included** |
| Conch (main) | `com.apple.security.device.audio-input` | **main is the process that asks**: it calls `askForMediaAccess('microphone')` (§9), and Apple's rule is that an app "needs to contain the appropriate key in its `Info.plist` file, and the appropriate entitlement enabled in macOS, before it requests authorization or attempts to use a capture device. Otherwise, the system terminates your app" ([Apple](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)). Main never opens the microphone under model B; it holds the entitlement in order to ask | **included** (corrected in review, 2026-11-11: the first draft left it out pending ME5) |
| any | `com.apple.security.cs.allow-unsigned-executable-memory` | "exposes your app to common vulnerabilities in memory-unsafe code languages" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-unsigned-executable-memory)); that current Electron does not need it is memory, not checked, and ME14 runs without it | **not included** |
| any | `com.apple.security.cs.disable-library-validation` | it is for a program that "loads plug-ins that are signed by other third-party developers", and "Gatekeeper runs extra security checks on programs that have it disabled" ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)). Everything in the bundle is signed with one Team ID | **not included** |
| any | `com.apple.security.cs.allow-dyld-environment-variables`, `com.apple.security.get-task-allow` | injection and debugging switches | **not included** |
| Conch | `com.apple.security.device.camera` | the camera phase (§9) | **not included yet** |
| any | the App Sandbox | this is Developer ID distribution, not the App Store; Chromium's own sandbox stays on | **not used** |

Input Monitoring, Screen Recording, Notifications and the Keychain need no entitlement of this kind; they are the privacy settings of §9 (memory, not checked, for the first two).

**Three sets, and electron-builder's two options do not make three.** The table needs: main with `allow-jit` and `audio-input`; Electron's helper apps with `allow-jit` alone; `conch-voice` with `audio-input` alone. electron-builder has `entitlements` (the app) and `entitlementsInherit` ("child entitlements ... for signing frameworks and bundles of a distribution"), and `binaries` ("paths of any extra binaries that need to be signed") names no entitlement file of its own ([`macOptions.ts` at 26.17.0](https://raw.githubusercontent.com/electron-userland/electron-builder/electron-builder@26.17.0/packages/app-builder-lib/src/options/macOptions.ts)). So a helper listed in `binaries` would be signed with the inherit set: `conch-voice` would get `allow-jit` it must not have and no `audio-input`, or Electron's helpers would get `audio-input` they must not have. Per-file selection is needed, and there are two documented ways to get it, both in that file:

1. **Sign `conch-voice` first, by itself, and tell electron-builder to leave it alone** (proposed). The release job runs `codesign` on the helper with the hardened runtime, the Developer ID and its own one-line plist before packaging, and the configuration lists it under `signIgnore` ("regex or an array of regex's that signal skipping signing a file") instead of `binaries`. The app's signature then seals the already-signed helper. It needs no code in the build, and the helper's entitlements are visible in one `codesign` line.
2. A custom `sign` function ("the custom function ... to sign an app bundle") that chooses the plist per file. More flexible; it is code that runs with the signing identity, and it replaces electron-builder's own signing rather than adding to it.

That `@electron/osx-sign` can choose options per file was not read here (memory, not checked) and is not relied on. Whichever route MF13 takes, **the check is the same and is ME14's**: `codesign -d --entitlements -` on main, on each Electron helper app and on `conch-voice` shows exactly the set in the table, and the app's signature verifies with the helper inside it. The plists are three small files in `desktop/build/`, named explicitly; electron-builder's own defaults are **not** relied on, because what they contain was not read here.

## 14. Proposed amendment to ADR-006 (text for a later PR; ADR-006 is not edited here)

To follow the Windows amendment Nick asked for as a PR on 2026-11-11 (#756), in the same form:

> **Platform (amended):** Linux with PipeWire, through `dmn-audio`; Windows 11 x64 with WASAPI, through the `wasapi` crate, and Raw Input through `winit`; and **macOS on Apple silicon (15 and later) with Core Audio, through the `cpal` crate, and a listen-only Quartz event tap, through the `core-graphics` crate**; each behind `cfg(target_os)`. The audio and key-source layers are the only platform-specific code; the gate, mixer, session loop and control protocol are shared. Other platforms, and Intel Macs, still need a decision of their own.
>
> **Dependencies (amended):** the allowlist gains `cpal`, `core-graphics` and `core-foundation`, macOS-only [and `rustix`, if it is the route taken for the helper's uid]. `scripts/voice-pins.sh` pins the macOS libwebrtc archive by hash as it pins the others. `deny.toml` checks all three targets.
>
> **Consequence added:** CI gains a macOS job for `voice/`; the Linux leg of `make check` is unchanged. Building for macOS needs Xcode and the `-ObjC` link argument the LiveKit SDK requires there.
>
> **Transport on macOS:** as on Linux for an Electron owner: commands on standard input, the only channel that carries authority; events on an owner-created Unix socket in a verified per-user directory; the attach line binds the connection to the spawned process and is not authentication.
>
> **Permissions on macOS:** the helper is the process that uses the microphone and the event tap, under the app's identity. It requests Input Monitoring and never Accessibility. A change that would need Accessibility, an active event tap, a system extension or a disabled system protection is a new decision.

If voice processing (MF12) is later accepted, the amendment names `coreaudio-rs` too. Written here as text for Nick to accept, reject or edit.
