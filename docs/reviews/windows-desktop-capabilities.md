# Windows desktop capability matrix and security review (issue #775)

- **Reviewed:** the proposed design [docs/design/windows-desktop.md](../design/windows-desktop.md), against the sources it cites, on 2026-10-28.
- **Reviewer:** protocol-designer agent (Claude Fable 5.1), desk research only. **No Windows machine was available.** Nothing in this document was run on Windows. Every row whose evidence needs native Windows is **pending-hardware** and names the experiment that would settle it; a row is **verified-by-docs** only when a cited official page states the mechanism, which is a statement about the API, not about a pinned Conch build on a real machine.
- **How to read the status column.** `proposed`: the design says how, nothing checked yet. `verified-by-docs`: the mechanism is documented as stated, by the cited page. `pending-hardware`: needs a Windows 11 x64 machine, a headset, a second listener, or a game. `unsupported`: the design says it will not be offered. The hardware run that fills this matrix is follow-up F14 in the design note.
- **Versions to record with every hardware result:** Windows version and OS build (`winver`), Electron and Chromium (`process.versions`), `conch-voice` version and hello line, GPU and driver, audio devices (endpoint IDs and friendly names), keyboard and mouse models, the game and its anti-cheat, and the commit of this repository.

| X4 | No localhost listener, no secret in argv, a child environment built from an allowlist | named pipe, not TCP; argv is `conch-voice.exe managed --events-pipe <name>`; the nonce and the token are in an environment the owner builds from empty by a case-insensitive allowlist (Windows names are case-insensitive, memory; `Conch_Token` would pass a case-sensitive prefix filter) | design §3.3, §3.4, §3.7; `std::env::set_var`/`remove_var` are `unsafe fn` ([std](https://doc.rust-lang.org/std/env/fn.set_var.html)), so the helper cannot scrub itself | proposed | remote SMB clients are not rejected by libuv's pipe (no `PIPE_REJECT_REMOTE_CLIENTS`): residual in §2.1 |
| X5 | Owner death (crash, kill, power) stops capture and ends the helper within the contract's bounds | EOF on standard input; EOF or write error on the events pipe (its read half, read concurrently); the helper's watchdog; possibly a kill-on-close job inherited from Electron's main process | design §3.6; kernel closes a dead process's handles; children join their parent's job by default ([Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)) | **pending: E6** | `VoiceControlGateShutMS` 100, `VoiceControlCaptureStopMS` 500, `VoiceControlOwnerLossExitMS` 3000; measure with a key held and while transmitting; record `IsProcessInJob` for the pinned Electron's main process and the helper, and the job's limits |

| X7 | Bounded stop from the owner; only its own process is ever killed | `leave`, close stdin and the events server, `child.kill()` at `VoiceControlStopKillAfterMS`; no graceful signal exists ("terminate the process forcefully and abruptly") | [Node child_process](https://nodejs.org/api/child_process.html) | verified-by-docs for the mechanism; **pending: E6** for the measured bound | never `taskkill`, never by name; `windowsHide: true` so no console flashes |

## 2. Security review

This is a design review; no code exists. Each item is a threat, who can mount it, the design's answer, what remains, and the status.

### 2.1 Managed transport threat model

| Threat | Who | Design's answer | Residual | Status |
| --- | --- | --- | --- | --- |
| **The invariant.** Authority arrives only on standard input, from the spawning process; the events pipe is helper-to-owner and carries none | — | commands (join, mute, devices, leave) exist only on stdin, whose write end the owner holds from spawn and to which nothing connects by name afterwards; libuv's stdin is itself a named pipe under `\\?\pipe\uv\` with the same default DACL ([libuv `pipe.c`](https://raw.githubusercontent.com/libuv/libuv/v1.x/src/win/pipe.c)), trusted because of the handles, not the name | a hijacked or observed events pipe cannot cause a join, a publish or an unmute; it costs state-line confidentiality (no secrets, no free text) and availability (no attach, the join fails closed) | by design |
| Another **user** opens the events pipe | any local user (default DACL: "read access to members of the Everyone group and the anonymous account"; no write; and creating an instance needs `FILE_CREATE_PIPE_INSTANCE`, which they lack: [Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)); possibly a remote SMB client, since libuv does not set `PIPE_REJECT_REMOTE_CLIENTS` | **the DACL is the cross-user boundary:** they open read-only, cannot deliver a line and cannot hijack an instance; the owner writes **nothing** on the events pipe, to anyone, ever, so they read nothing | the pipe's existence and name reveal that Conch is installed and a voice session may be running | pending E2: a second standard user's `GENERIC_WRITE` denied and `GENERIC_READ` granted; the effective DACL and integrity label of the pinned Electron's pipe recorded |
| **Same-user** code hijacks the events pipe | same-user processes | none, and none claimed: the creator owner has full control, libuv's listener is `PIPE_UNLIMITED_INSTANCES`, so `CreateNamedPipeW` on the owner's name succeeds and the helper's `CreateFile` may land on the hijacker's instance, which then receives the attach line and every event. **The nonce authenticates nothing to the helper.** Same-user code can equally read `CONCH_TOKEN` from the environment or the helper's memory | **same-user is out of scope**, on Windows as on Linux; named here so that the attach line is never mistaken for a defence against it | pending E2: same-user `CreateNamedPipeW` on the name succeeds (record it) |
| A same-user process connects **without** the environment (a stray tool, a debugger's probe) and the owner takes it for the helper | same-user, accidental | attach line: 256-bit nonce from `crypto.randomBytes` in the helper's environment, compared with `crypto.timingSafeEqual`, within the hello timeout; a connection without it gets one bounded line (4096 bytes) read and is closed; the listener closes on attach or on the deadline; `PIPE_UNLIMITED_INSTANCES` means the real helper still connects; the owner never writes; the nonce is redacted from diagnostics and covered by `sensitive.json` | this is a **spawn-to-pipe binding and defence in depth, not authentication**; the schema text and the ADR amendment say so | proposed; needs the `security-reviewer` pass F4 asks for |
| A process **squats the name** before the owner listens | any local user | `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first instance makes the owner's `listen` fail ("creation of the next instance fails with ERROR_ACCESS_DENIED"); the owner draws a new random name | an attacker racing every name costs the owner retries; bounded by the hello timeout, after which the join fails closed | verified-by-docs for the flag |
| Connection exhaustion against the attach | any local user | bounded: one line, 4096 bytes, closed; accepting stops once the helper attached | a flood before the helper attaches can delay it past the hello timeout: denial of a join, never an open microphone | accepted |
| **Handle inheritance** leaks the owner's pipe ends into another process, so the helper outlives its owner | Electron spawns many children concurrently | the events-pipe EOF is a second, independent owner-loss signal; the listener is not inheritable; the Win32 means to scope inheritance (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`: "a list of handles to be inherited by the child process", [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)) is not reachable from Node | a leaked stdin end alone no longer keeps the helper alive, because the events pipe ends; a leak of both is not possible for the listener | pending E6 (measure owner-crash exit time with Chromium children alive) |
| **No localhost listener** | — | named pipes, no TCP; a browser cannot open `\\.\pipe\` | none | by design |
| **Secrets in argv, or inherited through the environment** | any local user reading command lines; a stray variable in the owner's environment | argv holds the executable, `managed`, and a pipe name that carries no authority; token and nonce are in the environment, as `CONCH_TOKEN` already is on Linux; the child environment is **built from empty by a case-insensitive allowlist** (`SYSTEMROOT`, `PATH`, `TEMP`, `TMP`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `PROGRAMDATA`, `COMSPEC`) because Windows names are case-insensitive (memory) and a `startsWith('CONCH_')` filter would pass `Conch_Token`; the helper cannot scrub itself (`set_var`/`remove_var` are `unsafe fn`, [std](https://doc.rust-lang.org/std/env/fn.set_var.html)) and spawns nothing, and any child it ever spawned would get `env_clear()` plus the allowlist | environment is readable by the same user and administrators (as on Linux) | by design; the allowlist is confirmed at E1 |
| The helper is **impersonated by the pipe server** | a same-user process holding an instance (above) | tokio's client sets `SECURITY_SQOS_PRESENT` with `SECURITY_IDENTIFICATION` by default ([ClientOptions](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.ClientOptions.html): without QoS flags a server could gain the client's privileges) | none beyond same-user scope | by design |
| Owner cannot verify the **client's pid**; helper cannot verify the **server's** | — | not available to Node or to safe Rust; the nonce stands in | a Win32-capable owner (the Go TUI) could add a user-SID DACL, `PIPE_REJECT_REMOTE_CLIENTS` and `GetNamedPipeClientProcessId` | noted as hardening, not required for the bounds |
| **Process ownership**: killing the wrong process | — | `child.kill()` acts on the process libuv spawned; never by name or by pid lookup; no new helper until the old one is reaped | — | by design |
| A secret on the channel | — | the attach nonce is a one-time binding value, spent on acceptance and redacted from the owner's diagnostics; no login token, join token or room name ever crosses; `sensitive.json` for the new shape asserts it | a transcript shows a dead nonce | proposed; reviewer to confirm the framing |

### 2.2 Input risks

| Risk | Design's answer | Residual | Status |
| --- | --- | --- | --- |
| **Keylogging surface.** Raw Input delivers every keyboard and mouse transition on the desktop to the registered window | only bound transitions leave the input module (`KeyEvent`, `DeviceState`); no scan code, count or time is kept, logged or sent; same discipline as `keydev.rs`; no exclusive grab, no cross-session reach (Raw Input is per desktop session) | any same-user process can register for Raw Input itself; Conch adds no capability it did not have | by design; the README states it as the Linux one does |
| **Hooks.** `WH_KEYBOARD_LL`/`WH_MOUSE_LL` would be silently removed after a 1000 ms stall ("There is no way for the application to know whether the hook is removed", [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)), are "a shared resource" affecting every application ([SetWindowsHookExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)), and are the pattern anti-cheat looks for (memory) | not used | none | by design |
| **Anti-cheat.** A background raw-input listener next to a protected game | passive, documented, user-mode API; no DLL, no hook, no handle to the game; per-title testing with versions recorded; incompatible titles labelled, never worked around | vendors do not document what they tolerate; a title that flags any background input listener is **unsupported** for PTT and said so | pending E9, one row per title |
| **Elevated foreground / secure desktop.** A release delivered nowhere | `max_transmit_secs`; owner `set_mute` on lock, `leave` on suspend; `transmitting` visible; device-removal handling | a held key across a UAC prompt may transmit up to `max_transmit_secs` if the `BREAK` is lost | pending E8 |
| **A key already held at registration, or a stalled input thread.** Repeats taken for a press; a hung message loop holding the gate | a binding starts unknown and is armed only by an observed `BREAK`; a stall of one `VoiceControlOwnerPollMS` while held is `ptt: lost` with `ptt_problem: read_failed` and shuts the gate | one unused press after start if the key was held | pending E7 |
| **The input dependency's own surface.** Wrong flags, a hidden hook, logging of scan codes | audited at the pinned version before allowing: exactly `RIDEV_INPUTSINK \| RIDEV_DEVNOTIFY`, no `RIDEV_NOLEGACY`, no `RIDEV_CAPTUREMOUSE`; no `SetWindowsHookEx` in the compiled vendored source; logging features off; the no-scan-code output test rerun on Windows | API churn at the next version re-runs the audit | pending F6/E7 |
| **Injected input.** Another process synthesising a `MAKE` for the talk key (`SendInput`) opens the gate | Raw Input reports injected input as input (it is what the keyboard driver or `SendInput` produced) | a same-user process that can inject input can also read the token; not a new boundary | accepted, stated |
| **Binding capture.** Reading keys to configure the binding | done in the focused Electron window during configuration, by the renderer's own key events; the helper's raw-input stream never leaves it | none beyond the renderer's normal input | by design |
| **A dependency's own behaviour.** `winit` (or another crate) is in the helper's process | pinned, licence-checked, `cargo deny`; `default-features = false`; its raw-input registration read in source for the pinned version ([`raw_input.rs`](https://raw.githubusercontent.com/rust-windowing/winit/v0.30.13/src/platform_impl/windows/raw_input.rs)) | a windowing framework's surface in an audio helper; 0.31's API churn | pending F6's decision |

### 2.3 Other review notes

- **Credentials:** DPAPI protects against other users, not same-user malware; the design says so to the user rather than implying more ([safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)). The synchronous API is going away; the asynchronous one is specified.
- **Microphone privacy toggle:** honoured by reporting, never by bypass; Microsoft's own note that desktop apps "might still be able to access" the microphone means the toggle is not a guarantee Conch can rely on either way.
- **Companion participant (model B):** a second grant for one person is new server surface; F8 carries its own security review (identity derivation, no privilege beyond the parent session, teardown on revocation, folded presence so that occupancy and moderation see one person).
- **Installer and updates:** per-user install writes nothing outside the user's profile; manual updates verify signature and digest; previews are labelled unsigned and come with no instruction to lower protections.

## 4. Verdict

The design is **ready for review as a proposal**, not for acceptance: three decisions block implementation children becoming Ready, and none can be settled from documentation alone.

1. **Dependencies:** `wasapi` and the Raw Input route (`winit`, another crate, or a reviewed `unsafe` leaf with an ADR-006 amendment). Owner's sign-off.
2. **Media ownership** with #769: model B (companion participant) or model C (Chromium media, helper as input). The conchd follow-up F8 exists only under B.
3. **Hardware evidence** E1–E12: every push-to-talk, audio, transport-bound and lifecycle row is pending until a Windows machine runs them.

Nothing in the proposal weakens the published contracts or the fail-closed rules; the two new wire shapes are additive and versioned; Linux behaviour and `forbid(unsafe_code)` are unchanged. The invariant the transport rests on is that authority arrives only on standard input from the spawning process; the attach line is a spawn-to-pipe binding, not authentication, and the pipe's DACL is the cross-user boundary.

**Review round 1 (2026-10-28)** corrected, in both documents: the events pipe is opened with tokio's overlapped client, not a synchronous `std` handle (X2, E2); the attach line is reworded from authentication to binding, with the same-user instance hijack named and the DACL as the cross-user boundary (X3, §2.1); the child environment is an allowlist, not a filter (X4); a held-at-start key cannot open the gate and a stalled input thread shuts it (P10, P13); LiveKit has no video-only subscribe grant, so the companion is B1 or B2 (M3); conchd issues a second session rather than refusing it, and LiveKit displaces (M2, E10); include-tree audio is refused for the call's own process tree (S3, E5); endpoint IDs are validated, not assumed to fit (A3); 26H1 and 26H2 are released and pending validation (T5, T6); the configuration layer's Windows port is listed as work (design §2.7, F15).

**Review round 3 (2026-10-28)** corrected: F17 applies the same subscription filter to the publications present at join (`RoomEvent::Connected`), not only to `TrackPublished`; the share-audio rule holds only in a session whose companion owns share audio, and every other session (Linux TUI, standalone helper) keeps playing remote share audio as today; configuration conflict detection keeps comparing the file's text, not metadata alone.

**Review round 2 (2026-10-28)** corrected: one playback owner per audio source, with the helper's `auto_subscribe` and mix-everything behaviour named and F17 added (M1, M3, E10); the browser-tab fallback replaced by an explicit hand-over, since a watch-only tab connects as the person and displaces the helper (M4, model D and B1, E10); the configuration race closed by `FILE_FLAG_OPEN_REPARSE_POINT` plus an attribute check on the opened handle, with temp-file-then-rename kept and an inspect-then-swap test (design §2.7, F15).
